## What changed on main since the last peer-parsing pass

`REVIEW-2026-11-01` reviewed `0e10897`. Thirteen commits have landed since. The ones that move peer bytes, session state, or a peer-triggered allocation:

- `b00eea2` (`#493`) — call spends use the consented per-block ceiling. Spend authority. #503 already covers the payment side. No parser change.
- `5b128b1`, `7c1fd63` (`#498`, `#500`) — a grant-funded call's closing signal is paid by its grant, and an unpayable closing quote is refused. #503 reviewed this tree through `b3f1ad1`. The only peer-parser change in that work is below: a call-block invoice is refused when this node has no readable session with the caller.
- `5179ed9` (`#519`) — the Double Ratchet send chain advances only after AEAD succeeds, and that advanced chain is saved before the ciphertext is returned. A failed save puts the chain back and withholds the ciphertext.
- `9083dfa` (`#520`) — a prekey bundle or session init whose identity key is not the X25519 key from this connection's Hello is ignored. A bundle that reuses its identity key as the signed pre-key is ignored, including the same curve point with the top bit flipped.
- `c5d2ce9` (`#514`) — a lost session is recovered on the live connection. A new session is held aside until the peer proves it (a SessionAck for one we initiated, a message that decrypts for one we accepted). The previous session keeps reading for one hour. One undecryptable envelope, or one unreadable `RatchetInit`, marks the session and sends a `PrekeyOffer` instead of deleting it. A healthy session is replaced only after a second offer on the same connection, spaced by a self-heal tick.
- `9c923c9` (`#521`) — a file send reports the routing fee actually paid. The received-file record is unchanged.

`2eae3fe` (`#505`), `d4597af` (`#524`), the rc21/rc22 notes, and `4fcb922` (`#527`) do not change a parser. Dependency waivers stay with #510, #515, and #484.

## Low — fixed in this PR

### L1 — Each further unreadable session frame asked for a new prekey bundle

`handle_ratchet_init` (`crates/konsensus-node/src/session_handler.rs`) and `note_unreadable_envelope` (`crates/konsensus-node/src/msg_handler.rs`). #514 keeps the session when a `RatchetInit` or a paid envelope cannot be decrypted, marks it, and sends our prekey bundle. The mark stayed set, and every later failure sent another bundle and wrote another warning. A privileged peer can send `RatchetInit` frames without a further payment. The self-heal tick already offers again every 15 seconds while the mark is set.

**Fix.** The first failure still marks the session and sends one offer. A later failure, while that mark is set, returns without another offer or another warning. A `RatchetInit` that does decrypt still clears the mark, so the recovery frame is not dropped. `a_second_unreadable_ratchet_init_asks_only_once` and `a_second_undecryptable_envelope_asks_only_once` cover both paths.

### L2 — The healthy-session offer witness had no entry cap

`OfferWitness` (`crates/konsensus-node/src/session_handler.rs`). It records the first offer from a privileged peer whose session looks healthy, and acts on a second offer on that same connection. The negotiation and peer-exchange maps clear above 10,000 entries. This map only dropped entries older than the witness window, and that prune runs on the 300-second cooldown tick. A burst of distinct privileged peers inside that window grew the map by one entry each.

**Fix.** A peer that is not already recorded gets no slot once the map holds 10,000 entries, the same cap as the other cooldown maps. Past the cap the cleanup tick clears it. Missing a slot leaves the healthy session in place. `offer_witness_stops_at_the_cap` fills the map, refuses one more peer, and still accepts the second offer from a peer that already has a slot.

## Info

**I1 — A failed `RatchetInit` is still decrypted while the session is marked.** Skipping that decrypt would also skip a later init that does read, which is what clears the mark. Each attempt stays inside the existing skip cap (`MAX_SKIP` = 1000). The offer and the warning are what L1 stops repeating.

**I2 — Saving a send chain holds the session map until the store answers.** `SessionManager::encrypt` and `persist_session` (`crates/konsensus-crypto/src/session.rs`) take the map's write lock across the store write so an older chain cannot land on a newer one. A slow store stalls other session operations for that write. The previous code held a read lock across the same write, which already stalled encrypt and decrypt. Left as it is.

**I3 — The Hello-key check compares the raw 32 bytes.** `key_is_the_hello_key` refuses a bundle or init whose identity key is not the byte string from this connection's Hello, including a missing Hello key. The signed-prekey check uses the curve point, so the same point with the top bit flipped is refused. An honest peer sends the same bytes in the Hello and the bundle.

## Checked, not a finding

- `decode_frame` still rejects a length above `MAX_FRAME_BYTES` before the body is read. `RatchetInit` is still capped at `MAX_RATCHET_PAYLOAD_BYTES` (1 MiB). `Frame::CallMedia` is unchanged.
- One-time pre-key ids still start at a random point below half the `u32` range, and an init that names an id this boot does not hold consumes nothing. A replacement is one held session per peer, overwritten in place, and the negotiation cooldown is still 10 seconds.
- `answer_prekey_offer_for_recovery` answers a lower id's offer with our bundle only after the connection and the negotiation cooldown, and only through `EagerOfferLimiter` (one per peer per 10 seconds, 16 per second across peers, 10,000 remembered peers).
- The unpaid TCP doorway is unchanged: `DosEdgeConfig` still caps pending connections, handshakes, and per-IP accepts before a peer is admitted. Session frames are still dropped unless the connection is privileged.
- A call-block preview tries the current session, then one held-aside session, then the retired session while it can still read. A failure leaves the live ratchet where it was. `TooManySkipped` stays retryable; other decrypt failures on a call block from the higher id are still the terminal `undecryptable:` refusal #514 added.
- `FileRecord.size_bytes` and the call-block invoice amount are the open items in #497. This PR does not touch them.
- No new `unwrap` or slice panic on the session-init, prekey, or ratchet-init paths. A short ratchet message is still rejected at 40 bytes. X3DH still runs only after the identity key matches the Hello key and the signed pre-key verifies.
