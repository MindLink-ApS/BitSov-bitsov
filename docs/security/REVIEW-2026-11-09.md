### L1 — Genesis checks buffered an unbounded Esplora body

`#535` asks every configured Esplora URL for its height-0 hash and header, at startup and again before a later chain read when the check has expired or the connection was lost. `verify_esplora_api_urls` and `EsploraProvider::fetch` both used `response.text()` with no byte cap. The general Esplora client already had that pattern. The 2026-11-08 note left it open, because a cap on transaction and block documents has to fit those documents. The genesis answers do not. They are a block hash and an 80-byte header.

The source is the operator's chain endpoint, including a public Esplora the quickstart names. It is not a messaging peer. A large body on this path is still allocated inside the node process, on a request the node now makes before it will use that source.

**Fix.** `MAX_GENESIS_ANSWER_BYTES` is 1024. `read_limited_text` returns an error when `Content-Length` is larger than that, without reading the body, and stops a chunked body at the same cap. `esplora_genesis` trims surrounding whitespace, then refuses that trimmed string when it is longer than the cap, before it hex-decodes. Whitespace around a short answer does not make it oversized. An oversized answer leaves that endpoint unverified. It does not latch a network mismatch, so the other configured endpoints are not refused. Startup treats the failed check the same way it treats an unreachable source. Other Esplora reads, including fee estimates, block documents, and the recovery broadcast, still use `response.text()` with no cap. That remains the open item below.

## Checked, not a finding

- `decode_frame` is unchanged. A frame longer than `MAX_FRAME_BYTES` is still rejected before the body is read. `MAX_CIPHERTEXT_BYTES` is still 6 MiB. File payloads still admit `data_b64` only up to the 4 MiB file budget. Calendar and porch bodies still go through `wire_json::from_slice`. `decode_frame` and the ciphertext cap are not in `2dc6304..20526a8`. `msg_handler.rs` and `session_handler.rs` are in that range only for the #467 cipher location.
- `RecordCipher::decrypt` rejects a body shorter than a nonce plus a tag. A v2 prefix with nothing after it is an error, not a slice panic. The associated-data length prefix is the full byte length of each part. Message ids and peer ids are fixed-width hex. The cipher's `expect` on the AES key runs only for a 32-byte key at construction.
- The record upgrade reads tables in batches. Tables that store raw bytes, including message ciphertext and file bytes, are read one row at a time. A row that is not valid JSON, not valid hex, or not a v2 blob is counted unreadable and does not panic the task. After the completion marker is written, `run` returns without scanning again.
- Session restore still skips a blob that does not decrypt. Plaintext session import still requires the migration feature and the environment flag, and now also requires the unbound format to still be allowed. A v2 blob is decrypted only for its own peer id.
- The offer-witness map still uses the 10,000-entry cooldown cap. This diff does not add a peer-keyed map.
- `NetworkGate` indexes only endpoints it was built with. An unrecognised chain name is an unverified or refused source, not a panic. Electrum's height-0 header uses the existing client reader. That reader already had no line cap, on every Electrum query, inside the vendored client. This PR does not patch that client.
- Postgres peer and room timestamps are formatted with `to_char`. A bad cast fails the statement. `list_peers` is still uncapped on purpose, as the comment on `PEERS_SELECT` already says. That query was not given a new shape beyond the timestamp expression.
- No new `unwrap` or `expect` on a peer-supplied length, count, or frame in the message or session handlers.
