## Medium — fixed in this PR

### M1 — An existing subsidy channel was missed when the peer changed pubkey case

`existing_channel_to_peer` (`crates/konsensus-node/src/onboarding/auto_channel.rs:489`). Before this PR the compare was `channel.peer_pubkey == ln_pubkey`.

LDK's `ChannelDetails.counterparty_node_id` displays as lowercase hex (`crates/konsensus-lightning/src/ldk.rs:2979`). The peer chooses the string in `LightningInfo`. `handle_lightning_info_received` (`crates/konsensus-node/src/session_handler.rs:1767`) accepts any 66-character compressed hex key, and `hex::decode` accepts `A`–`F`. The worker then calls `handle_peer_lightning_info` with that string.

The already-open path is what stops a second subsidy open when any channel to that Lightning key already exists, including an inbound channel the peer funded. It runs before the balance check (`auto_channel.rs:269`). A case mismatch fell through. `mark_invite_opening` then let the open proceed. Auto-channel is one task, so this is one extra open per still-pending invite, not a loop. The open is zero-push (`auto_channel.rs:400`), so the peer does not receive the capacity as a balance. The hub still locks `min(hint, max_channel_sats)` plus the funding fee in a new outbound channel, and the on-chain fee is spent. The subsidy is off unless the operator sets `enabled` and a non-zero cap, and the peer must be allowlisted and hold a pending invite. The funding poller already compares with `eq_ignore_ascii_case` (`funding_poll.rs:120`). This guard did not.

**Exploit sketch.** Subsidy is on, the peer is allowlisted, and an invite is still `Pending`. A channel to that peer's Lightning key already exists (the peer opened it inbound, or an earlier open stored the lowercase key while this invite was reset to pending). The peer sends `LightningInfo` with the same 33 bytes in uppercase. The node does not take the already-open path. It funds another channel at the clamped subsidy size.

**Fix.** The compare is `eq_ignore_ascii_case`. `already_open_channel_matches_pubkey_regardless_of_hex_case` stores the lowercase key, advertises the uppercase key, and gives the wallet enough balance to fund a second open. The open list stays empty and the invite is marked accepted.

## Medium — in flight

### M2 — A privileged peer still names the amount of a service invoice

`handle_invoice_requested` (`crates/konsensus-node/src/session_handler.rs:1393`), reached from `handle_invoice_requested_gated` when the peer is privileged and the purpose is not an admission quote (`session_handler.rs:1377`).

The handler calls `create_invoice(amount_msat, …, 3600)` with the peer's amount and a one-hour expiry. There is no per-peer rate limit on success, no cap on outstanding unpaid invoices, and no clamp to this node's price. The wire format allows `0` and `u64::MAX` (`crates/konsensus-message/src/wire.rs` `RequestInvoice` tests). Admission quotes are a different path and are already limited. The owner's `POST /api/v1/payments/invoice` caps amount at 1 BTC and expiry at 7 days (`payments.rs:119`). This peer path does not.

Creating the invoice does not send the hub's funds. The gate still refuses an underpayment for admission. The cost is wallet storage and HTLC slots: an admitted peer can mint invoices as fast as the session loop accepts frames, at any amount, each payable for an hour.

**Status: in flight in #403.** That PR adds a per-peer rate limit, a per-peer and node-wide cap on outstanding unpaid invoices, a price ceiling, and an admission floor. It was not re-implemented here.

## Low — open

### L1 — Some owner sends still dispatch again when the client retries

`POST /api/v1/payments/open-channel` (`payments.rs:986`) records an operation only when the body carries `operation_id`. Omitting it opens again. `POST /api/v1/payments/pay` for an unmetered (owner) caller (`payments.rs:294`) has no request id; a timeout retry pays the invoice again if the backend has not already seen the hash. Metered pay and keysend deduplicate inside the grant (`docs/SPEND_BUDGET_GRANTS.md`). Keysend without `request_id` is still two payments, on purpose, for legacy clients. On-chain send with `request_id` was fixed in `#375`.

Paired tokens cannot reach open, close, send-onchain, or release-local-spend: `ScopedAuth<Spend>` rejects a pairing (`auth.rs:718`). The retry is the owner, or a bug in the owner's client.

**Fix (not applied).** Require a client operation id on owner pay and on channel open, and store the outcome before broadcast, the way on-chain send already can. That is a client-visible change. This pass does not add a table or a migration.

## Info

**I1 — Liquidity acceptance shares the 6-sat non-payment ceiling.** `debit_liquidity` (`metered.rs:209`) reserves with `payment: false`, so `purpose_limit` caps the LSP fee at `min(per_call_max_msat, 6_000)` even when the owner set a higher per-call max and `allow_liquidity_fees`. A larger fee is refused. Nothing above the ceiling is dispatched. Raising it would be a new spend authority. Left as it is.

**I2 — LDK balance and channel capacity still multiply sats by 1000 with `*`.** `get_balance_msat` (`ldk.rs:1810`) and `channel_info` (`ldk.rs:2973`, `ldk.rs:2980`). A value above `u64::MAX / 1000` wraps in release and panics in debug. That threshold is about 184 million BTC. A real UTXO set and a real channel value do not reach it, and channel opens are rejected above `u64::MAX / 1000` before dial (`payments.rs:963`). LND and LNbits settlement and balance paths already use `checked_mul`. Not changed.

**I3 — Starter push is `push_sats as u64 * 1000`.** `starter_hub.rs:468`. `push_sats` on the grant row is `i64`, copied from config that `StarterHubConfig::validate` bounds to at most half of a capacity of at most 200_000. A negative row would wrap, but the peer does not choose the size. Not changed.

## Checked, not a finding

- A metered invoice debit is principal plus the fee ceiling, with `checked_add`, before `pay_invoice_with_fee_limit` (`payments.rs:303`). `RoutingFeePolicy::ceiling` (`lightning.rs:57`) lets the caller tighten the fee and not widen it. `resolve_payment` settles principal plus a known fee and leaves the reservation in place when the fee is missing (`metered.rs:407`, `settled_total`).
- A settled LND pay that omits `value_msat` or reports a different amount returns `LightningError::Backend` and does not release the grant (`lnd.rs:627`).
- Messaging grants cannot fund pay or keysend (`pairing.rs:3257`). The 6-sat cap is applied to every other reservation, including first contact, re-admission, files, porch pages, call invites, and room fan-out.
- Close and force-close go through `ScopedAuth<Spend>` (`payments.rs:1235`). A paired device is refused. The peer can still force-close on the Lightning protocol; that is the channel contract, not an API cap bypass.
- Auto-channel amount is clamped to the operator max, the fee rate is the lower of the invite and the operator ceiling, and a full or tight budget aborts before open. The worker handles one event at a time.
- The starter hub denies a peer who already has a channel, using a case-insensitive pubkey compare, and will not open above the configured channel-capacity limits.
- `bf700a1` keeps an in-flight keysend trackable. An empty hash is no longer returned for that race, so the caller is not told the payment is untrackable while LDK already has a `PaymentId`.
