### L1 — Later checklists still accepted status text

`scripts/release-sign.sh` and `scripts/verify-release.sh` accept a signature only when `[GNUPG:] VALIDSIG` field 10 is `B299274C200301714DC6F51A7C2D6F8AC842EF6E`. #447 taught rc10 through rc14 not to run the old copy-paste block. rc15's section 3 still said the check succeeds when `gpg --status-fd 1 --verify` exits 0 and the status contains `GOODSIG` and `VALIDSIG` plus the fingerprint. rc16 through rc18 said to verify `SHA256SUMS.asc` "against the fingerprint" and then `shasum -a 256 -c`. rc19 through rc22 said to use "the same primary-key check" and then `shasum -a 256 -c`. Section 2 of rc19 through rc22 already names field 10. Section 3 did not run the script, so the checkbox could still be satisfied by text anywhere in the status. rc20 and rc21 are the open Low from the 2026-11-03 review. rc22 copied that section after the review. The verifier those notes needed is on main as of `24a7ca4`.

**Fix.** Section 3 of rc15 through rc22 says not to treat `gpg --verify` success, or `GOODSIG` / `VALIDSIG` text, as proof, and to run `bash scripts/verify-release.sh <download-dir> RELEASE_KEY.asc` with the reviewed key file. The script does not fetch the key or the binaries. The old checklist lines stay underneath as the historical record. `scripts/test-verify-release.sh` requires that paragraph and that command in each of the eight notes.

### L2 — The rc14 upgrade note ran the download-directory binary

`docs/UPGRADING.md` ("Test Pi: retained rc13 → rc14 upgrade") told the operator to `chmod 0755 ./bitsov-linux-aarch64`, run `./bitsov-linux-aarch64 --version`, and `sudo install` that same path. The prose said to verify first. The commands are not chained to `scripts/verify-release.sh`, and they run and install the live download path. The home-node guide, changed in #447, installs `bitsov-linux-x86_64` only from the seal the verifier prints.

**Fix.** The note says not to run the block. The operator runs `scripts/verify-release.sh` and installs `bitsov-linux-aarch64` from the seal, as the home-node guide shows. The old commands stay as the record of the rc14 note. The verifier test requires that warning.

- `scripts/release-build.sh` still runs `rustup run` on the exact version in `scripts/release-toolchain`. `rust-toolchain.toml` is still channel `1.99.1`, not a floating channel.
