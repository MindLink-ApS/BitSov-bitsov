## Medium — fixed in this PR

### M1 — Locked listener accepted any Host

`serve_locked_mode` (`crates/konsensus-node/src/cli/locked.rs:148`) binds `config.api.listen_addr`, which must be loopback, and mounts `locked_router` there and on an internal `127.0.0.1:0` bridge. Before this PR the router (`crates/konsensus-api/src/locked.rs`) had no `LocalRequestPolicy`. `/auth/local` has had that policy since `#339`. The locked listener did not.

`GET /api/v1/node/lock` is unauthenticated and returns `node_id`, `fingerprint`, `locked_since`, `attempts_left`, and `hosted_by` (`locked.rs` `lock_status`). `docs/operations/home-node.md:53` tells operators and apps to poll those fields, so this PR does not remove them. Unlock and the unlock challenge still require a `RemoteTunnelClients` registration for the exact peer `SocketAddr`, then a device signature, then the password. A browser cannot register that map.

**Exploit sketch.** The operator runs the locked API on `127.0.0.1:3141`. An attacker page is loaded from the attacker's server on that same port (`http://evil.example:3141/`). Script on the page fetches `/api/v1/node/lock`. DNS for `evil.example` then answers `127.0.0.1`. The browser sends `Host: evil.example:3141` and `Origin: http://evil.example:3141` to the node. The response is same-origin, so CORS is irrelevant. The page reads the node id and fingerprint. It still cannot unlock: the challenge route returns 401 without a tunnel registration, and the password is never reached.

**Fix.** `LockedState::with_local_admission` installs the same Host and Origin allowlist the live API uses, built from `local_addr()` after bind (`cli/locked.rs:146`), not from a pre-bind port 0. `admit_local_or_tunnel` (`locked.rs:194`) runs on every locked route. A peer whose `SocketAddr` is a live tunnel registration skips the check, so the phone bridge's `Host: localhost` (no port) still works. Every other caller, including a missing policy, fails closed with the existing `local_host_forbidden` / `local_origin_forbidden` 403. The internal bridge port is not added to the allowlist.

`locked_router_allowlist_and_tunnel_only_unlock` covers a rebound Host, a foreign Origin, and a registered tunnel sending `Host: localhost`. `t14_locked_router_never_mounts_enrollment_or_health` still requires the real routes to 404 once Host matches, and a bad Host to 403.

**Left in place.** Another local UID that connects to the loopback port and sends `Host: 127.0.0.1:<port>` can still read the same JSON. TCP does not identify the peer uid. The operations guide tells that machine's operator to poll this route. See L3.

## Low — fixed

### L1 — Token challenges had no live cap

`PairingService::issue_token_challenge` (`crates/konsensus-api/src/pairing.rs:1863`) dropped expired rows and inserted another. The node-identity challenge map is capped at 128 (`auth_routes.rs` `AUTH_CHALLENGE_MAX_LIVE`). This map was not. A paired client, or many of them, could leave one entry per request for the 120s TTL. At the default 60 requests/second that is thousands of small rows, not a crash, and it does not mint a token.

**Exploit sketch.** A paired client calls `GET /api/v1/pair/challenge` in a loop. Each call stores a fresh 32-byte challenge until the TTL. Signing any one of them still works; the extra rows only occupy the process map.

**Fix.** After the expiry sweep, 128 live challenges return `PairingError::TooManyPending`, which the route already maps to HTTP 429. A client may hold more than one outstanding challenge; the cap does not replace an older one, so a device that signs the first of two challenges is unchanged. `token_challenges_stop_at_the_live_cap` covers the 129th issue.

### L2 — Seed KDF output was not wiped

`mnemonic_crypto::derive_key` (`crates/konsensus-node/src/mnemonic_crypto.rs:69`) returned `[u8; 32]`. `encrypt_mnemonic`, `decrypt_mnemonic`, and `owner_secret` use that key for AES-256-GCM and the owner-approval secret. The password and the plaintext mnemonic are already `Zeroizing`. The derived key was not, so it stayed in the stack slot until something else wrote it.

**Exploit sketch.** A local memory reader, after a decrypt or an owner-secret derivation, finds the 32-byte AES or owner key still in the process. That reader who can already dump the process can often read the password too. This is residual key material, not a remote bug.

**Fix.** `derive_key` returns `Zeroizing<[u8; 32]>`. Argon2id parameters are unchanged (64 MiB, t=3, p=1), so existing `.enc` files still open. `owner_secret` returns that wiped key directly.

### Info

**I1 — SAS digest compare is not constant-time.** `sas.rs:115` says the digest is compared in constant time. `confirm_device_sas` uses `==` (`crates/konsensus-api/src/pairing/device.rs:758`). A wrong v1 digest burns that operation and counts toward `sas_failures` (stop at 3). The digest is 32 bytes. A timing oracle is not a practical search.

**I2 — Argon2id parallelism is 1.** `derive_key` uses 64 MiB, t=3, p=1 (`mnemonic_crypto.rs:70`). RFC 9106's first option is p=4 at the same memory. Changing p, m, or t makes every existing `.enc` file and owner key fail to decrypt. Not a format change we can ship as a small fix.

**I3 — `POST /api/v1/pair/request` is unauthenticated.** That is the design: the 32-byte challenge is written mode `0600` and is not returned on HTTP. The short code is not in the HTTP body. On a non-loopback API, which config allows only when remote access is off, a caller can fill `MAX_PENDING_PAIRINGS` (32) and learn a data-dir path in the response text. The live router with remote access is loopback. Left as the documented pairing bar ("less exposure, not solved local security").

**I4 — SAS version mismatch names a missing operation.** `device_routes.rs:163`: a missing op plus `sas_version == 2` returns "SAS version mismatch"; a missing v1 op falls through to unknown-operation. The op id is 12 random bytes. Not worth a behavior change.

**I5 — `cargo audit` 0.21.2 cannot load the current advisory database.** Parsing stops on a CVSS 4.0 vector (`RUSTSEC-2026-0209` and anything the parser reaches after it). `cargo deny` 0.20.2 is the configured gate and completed the fetch. This is a scanner limitation, not a crate in the lockfile. CI workflow files were not modified.

## Checked, not a finding

- Owner routes take `ScopedAuth<S>`. `tests/scope_coverage_tests.rs` rejects a handler that takes a bare `AuthUser`. `/auth/local` mints only read and receive, and only after a loopback `ConnectInfo`, a matching Host (and Origin if present), and a process-wide 5/minute limiter (`auth_routes.rs:152`).
- JWTs are custom HS256. The MAC is checked before the payload is parsed, `alg` must be `HS256`, `crit` is rejected, and `exp` has no leeway. Bootstrap (`bst`) tokens are refused on the live router. A paired spend on an unmetered money route is refused.
- Password-fd reads at most 4096 bytes into a `Zeroizing` buffer and does not put the bytes in the error (`crates/konsensus-node/src/password.rs`). The password file refuses a symlink, a mode other than `0600`/`0400`, and a uid mismatch. Argv secrets still require `--insecure-argv` (`#340`).
- Unlock errors stay on the `unlock_failed` / `device_unknown` / `already_unlocking` / `unlock_rate_limited` set. A wrong device signature consumes the 5-per-key and 20-per-window budget (`locked.rs:318`). Argon2 runs only after that signature checks. The log line is `UNLOCK_VERIFYING` with no password.
- Owner short codes are 8 characters from a 32-symbol alphabet, 3 tries per grant, then disabled for the run after 10 failures. Comparison is a BLAKE3 digest. Claim codes are 18 characters, mode `0600`, and `Debug` redacts them. Second-device tickets are memory-only.
- Provisional Noise sessions are limited to the enrollment routes. Second-device approve is not on that list. CORS still rejects `*` and `null`. HTTP traces log method and path, not the query string.
- The default API limiter is 60 requests/second per IP and fails closed when `ConnectInfo` is missing. Remote pairing uses its own bucket. The Noise handshake stays at 20 per IP per minute.
