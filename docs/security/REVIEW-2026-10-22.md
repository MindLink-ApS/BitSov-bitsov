## Medium — fixed in this PR

### M1 — Starter and Lightning-info strings were bounded only by the 16 MiB frame

`Frame::StarterRequest` and `Frame::StarterStatus` (`crates/konsensus-message/src/wire.rs`, added in `#352`) and `Frame::LightningInfo` deserialized `network`, `ln_pubkey`, `ln_sig`, `state`, `reason`, `channel_id`, `funding_txid`, and `ln_addr` as plain `String`s. `decode_frame` rejects a length above `MAX_FRAME_BYTES` before the body is read (`wire.rs` `decode_frame`). It does not stop one field inside a legal frame from being the rest of that 16 MiB.

Those variants are valid frames. The reader does not charge them to the invalid-frame budget. It awaits them onto the control channel (`crates/konsensus-message/src/transport/messaging.rs:626`, capacity 256 at `transport/mod.rs:700`). A privileged `StarterRequest` is then `try_send`ed, whole frame, onto the hub queue (`crates/konsensus-node/src/session_handler.rs:445`, capacity 64 at `crates/konsensus-node/src/main.rs:1913`). The hub builds `canonical()` with the raw `network` string and passes it to `verify_message` (`crates/konsensus-node/src/onboarding/starter_hub.rs:86` and `:164`). `LightningInfo.ln_addr` is forwarded to auto-channel and dialed after `validate_host_port` (`crates/konsensus-node/src/onboarding/auto_channel.rs:267`).

The 64 MiB memory budget disconnects the reader, but only after the bytes have been accepted. Frames already queued are retained. An oversized starter frame never became "invalid", so the budget of 10 bad frames did not apply. Any peer that finishes Noise can send these frames. Privilege is checked after decode (`session_handler.rs:216`). The hub being off does not stop decode: a privileged peer is answered `starter_disabled`, and an unprivileged `StarterRequest` is disconnected, after the strings exist.

**Exploit sketch.** A Noise peer sends `StarterRequest` frames whose `network` or `ln_sig` is several megabytes, staying under 64 MiB per minute so the memory budget does not ban them on the first frame. Each frame is valid JSON. The control channel holds the decoded `String`s. On a hub, up to 64 of them wait on `starter_hub_tx` while `handle` runs `list_channels`. The same peer can put a multi-megabyte `ln_addr` on `LightningInfo`; auto-channel will accept any `host:port` shape and hand that string to the Lightning dial.

**Fix.** The bounded string visitors already used for porch quotes and peer labels now cover these fields. Caps, in UTF-8 bytes: network 32, starter pubkey 128, signature 1024 (the hub already refused a longer signature, but only after the copy), state 32, reason 64, channel id 128, txid 128, Lightning pubkey 130, Lightning address 262 (253-byte hostname, colon, five-digit port, and headroom). One byte past the cap fails `Frame::from_bytes`, so the frame counts as invalid and the existing ban applies. Honest values still round-trip: `signet` / `regtest`, a 66-character compressed key, a 104-character LDK zbase32 signature, and a normal `host:port`. `null` reason, channel id, txid, and `ln_addr` still decode. `starter_and_lightning_info_strings_reject_one_byte_past_the_cap` and `starter_status_null_strings_and_lightning_info_without_addr_still_decode` cover it.


**PR #363 review fixes.** The shared string helper now borrows a `serde_json::value::RawValue` from the frame slice and counts decoded UTF-8 bytes before deserializing into `String`. The count handles simple escapes, Unicode escapes, and surrogate pairs without allocating. Oversized plain and escaped values are rejected before either an owned string or serde_json's unescaping scratch copy is built. Nested peer labels use this same helper. Serde still scans the whole raw token, so CPU remains bounded by the frame limit; admitted strings may use scratch space proportional to their field cap. This borrowing path is intended for `Frame::from_bytes` / serde_json `from_slice` and `from_str`, not reader-backed or prebuilt `Value` deserializers. `Frame::from_bytes` also preflights container depth (128) without allocation: RawValue otherwise uses a growing stack for nested wrong-type or ignored values. Network callers use this canonical entry point; direct serde_json calls do not get the whole-frame depth preflight. Tests cover a 1-million-level wrong-type array, the depth boundary, and escaped quotes/brackets inside strings.

The allocation regression constructs inputs before measurement and decodes 4 MiB plain, newline-escaped, Unicode-escaped, and surrogate-pair-prefixed values through required, optional, and nested-label fields. It rejects any individual decode allocation above 4 KiB (the old escaped path allocated 4,194,305–4,194,308 bytes). Escaped field names and exact decoded-byte boundaries are covered too. Other uncapped fields and JSON keys retain their existing outer-frame bounds; this is not a whole-frame allocation guarantee.

`StarterStatus.reason`, `channel_id`, and `funding_txid` retain `serde(default)`, with omitted-each and omitted-all tests in addition to explicit nulls. A real 253-byte DNS hostname with `:65535` (259 bytes total) now decodes. Config loading rejects over-cap `lightning.advertised_address` and `lightning.listening_address` (which can be advertised as the fallback), including the pre-identity bootstrap load path, with a field-specific error that states the byte limit.

The 16 MiB frame cap is unchanged. Other string fields called out on 2026-10-20 (call SDP, BOLT11, invoice reason) are not given new caps here.

## Low — fixed

### L1 — Starter admission does Lightning and signature work before the ten-minute throttle, and a full queue drops the request

`StarterHub::handle` (`crates/konsensus-node/src/onboarding/starter_hub.rs:160`) verifies the Lightning signature, reads the invite, and calls `list_channels` (`starter_hub.rs:219`) before the ten-minute per-requester check (`starter_hub.rs:233`). That check returns only when no earlier deny is set. A repeat from an invitee who already has a channel skips the throttle and writes another refused row. `session_handler.rs:445` uses `try_send`. When the 64-slot queue is full the frame is discarded and the peer is not told and not disconnected.

**Exploit sketch.** The hub is enabled and the attacker is a privileged invitee. They send a new `StarterRequest` as fast as the session loop will take it. Each one that the worker actually runs pays for a signature check and a channel list before the cheap throttle. Requests that arrive while the worker is inside `tick` (channel open is allowed 120 seconds) fill the queue and then vanish. Reconciliation on that same task waits behind the flood. A peer who is not invited never reaches this; unprivileged starter frames are refused first (`session_handler.rs:216`). The feature defaults off.

**Status: fixed on `fix/starter-hub-throttle-first`.** After the cheap network/version/length checks, `StarterHub::handle` reserves a ten-minute window keyed by the authenticated Noise session `peer_id` supplied by the privileged control event, never by the claimed Lightning key. The window precedes signature verification, invite lookup, `list_channels`, `list_peers`, and balance work, including every new-ID `already_served` path. The atomic in-memory reservation covers invalid signatures and backend failures without a grant row, survives peer reconnects, expires after ten minutes, and does not slide on refusals. The existing `LatestRequester` query preserves persisted windows over hub restarts; attempts without a grant row remain process-local. No database migration or new table.

A same-ID status replay is a cheap stored-grant read bound to the Noise peer, stored Lightning key, and network. It does not repeat signature verification or Lightning work and cannot admit another grant. This preserves lost replies and original-grant adoption without exhausting the newcomer's bounded retry budget. During a throttled new-ID attempt, the same three-way identity binding also permits a cheap lookup of an existing original grant and an `already_served` adoption reply. This performs no signature or Lightning work; it prevents the final automatic successor from exhausting its retry budget when a delayed ancestor was just admitted. Channel/invite-only `already_served` checks remain behind the window. A full or closed worker queue now disconnects the sending peer and increments `konsensus_starter_requests_total{result="refused"}` plus `konsensus_starter_refusals_total{reason="queue_full"}` or `{reason="worker_unavailable"}`.

Regression coverage counts signature, channel, peer, and balance calls during floods; exercises invalid signatures with rotating claimed LN keys, concurrent requests, independent peers, served invites/channels, and exact window expiry/restart behavior; verifies full/closed queue disconnects and counters over real Noise sessions; and checks #364's 10/20/40-minute successors, lost replies, and delayed original-grant adoption even on the final automatic successor.

## L1 follow-up: on-chain send retry identity

`POST /api/v1/payments/send-onchain` now accepts an optional client `request_id`
(UUIDv4). Clients must persist one ID per intended send and reuse it after a timeout.
The binding covers the address, amount and optional fee-rate override, including
whether the estimator was selected. UUID spellings are normalized. A different
body under the same ID returns HTTP 409 `operation_mismatch` without a send.

Compatibility choice: missing or null IDs remain allowed for existing clients.
Each such call logs a warning that it has no retry protection; these clients must
not retry automatically. The existing fee-rate validation and backend amount
checks are unchanged.

There is no generic owner payment-operation table on this branch: owner
keysend/pay use `request_id` only for metered debits. On-chain sends reuse the
existing encrypted `channel_open_operations` request/result store and atomic
insert/resolve pattern, with `send-onchain:<canonical UUID>` keys isolated from
channel-open UUIDs. No SQL migration is needed. The existing `opened` state holds
a returned txid, including an unconfirmed broadcast; `uncertain` holds ambiguous
outcomes. Only proven pre-dispatch refusals release their pending row; success,
pending and ambiguous outcomes retain their request bindings.

Only the insert winner calls `send_onchain`. Dispatch and receipt recording run
in a task that survives HTTP cancellation. A saved success replays the original
HTTP 200 body; a saved `BroadcastUnconfirmed` replays its original HTTP 202 and
txid. If the receipt write fails after broadcast, the caller still receives that
original body and txid. The failure is logged and persistence is retried in the
background after 100 ms, 500 ms, 1 s, 5 s and 30 s. These retries only write the
receipt; they never call the wallet. Exhaustion or process exit can still leave
a pending row requiring manual inspection.

`PaymentNotDispatched` and `NotReady` prove pre-dispatch refusal and delete the
pending row, allowing the same ID to be retried after the cause is fixed. A
failed deletion is logged and leaves the row blocking dispatch. Deletion is
not retried in the background: a delayed delete must never remove a later
attempt's reservation. Older saved refusal receipts remain readable.

Recovery is read-only and never broadcasts. A crash after inserting the record,
before dispatch or before recording the result, leaves HTTP 202 `pending`; an
ambiguous backend error leaves HTTP 202 `outcome_uncertain`. Pending may mean
in-flight or an unrecorded outcome, not proven non-dispatch. There is no backend
lookup by client UUID, so recovery cannot safely infer a txid or retry from an
address/amount match. Inspect the wallet and chain before choosing a new ID.
Ambiguous backend error text is retained in the row's `last_error`, preserving
any txid included by the backend for operator inspection. It is not parsed as
proof of success or non-dispatch. Database and task failures returned as HTTP
500 use fixed text; diagnostic details stay in logs.
A retry may return a saved receipt even while the wallet is not money-ready.

Retention: each dispatched request ID leaves a permanent row. There is no TTL
or pruning, so storage grows with send history, including unresolved attempts.
Do not delete these rows to reclaim space: losing the binding permits an old ID
to send again. Any future retention policy must preserve replay protection and
isolate the `send-onchain:` namespace from channel-open reconciliation.

Regression coverage: `crates/konsensus-api/tests/onchain_operations.rs` uses a
mock wallet and real SQLite records to cover concurrent retries, request binding,
restart with a crash-left pending row, persisted results and ambiguous errors,
released refusals, HTTP cancellation, insert races, failed record/receipt writes,
background persistence recovery, UUIDv4 validation, and missing/null legacy IDs.
No live-chain sends are part of this verification.

Round-1 verification: `cargo test -p konsensus-api -p konsensus-storage
--no-fail-fast` passed with local-socket access: **1,845 passed, 0 failed,
3 ignored**, including all 14 on-chain operation tests. The initial sandboxed
run failed in seven API targets because local socket operations were denied;

## L4 follow-up: remaining peer-frame fields

Based on #363 head `42f779db`; intended as a separate follow-up after #363.
All variable-size fields reachable through `Frame` now have deserialize-time
bounds, including nested capabilities, price-map keys, prekey/session JSON,
peer-exchange quotes and UKM envelopes. Fixed-size hex types decode directly
into stack arrays rather than first allocating a `String` and decoded `Vec`.

| Fields | Maximum decoded bytes / elements |
|---|---:|
| Invoice correlation IDs and call session IDs | 256 bytes |
| MessageReject / Disconnect / InvoiceError / CallEnd reasons | 1,024 bytes |
| RequestInvoice purpose | 1,024 bytes |
| InvoiceResponse payment hash | 128 bytes |
| InvoiceResponse BOLT11 | 65,536 bytes |
| CallOffer / CallAnswer SDP | 65,536 bytes |
| ICE candidate | 4,096 bytes |
| Custom capability / price-map key | 128 bytes |
| Prekey/session JSON key / string value | 256 / 4,096 bytes |
| UKM ciphertext (Message, Gossip, paid peer-exchange request) | 6 MiB |

Admission correlation IDs contain two hex identities, a timestamp and a nonce
(up to 190 bytes), so a UUID-only limit would break first-contact payments.
The ciphertext cap retains headroom for the file API's base64/JSON encoding
and ratchet overhead. The unchanged 16 MiB outer frame limit still applies.

[BOLT11](https://github.com/lightning/bolts/blob/master/11-payment-encoding.md#tagged-fields)
permits multiple route-hint tags and has no overall character limit. The 64 KiB
invoice policy accommodates hundreds of private hops; a signed 72-hop fixture
(over 4 KiB, within the installed parser's checksum-code limit) exercises real
long-invoice compatibility. Peer-exchange quotes retain their existing 8 KiB BOLT11
cap because their bounded reply queue uses a single Noise record. Existing
starter, LightningInfo, porch, snapshot, vector-count, reference-count and JSON
node/depth bounds remain in place.

Every rejection surfaces from `Frame::from_bytes` and consumes the existing
invalid-frame budget. A transport regression sends oversized, otherwise valid
InvoiceError frames and observes a ban. The initial L4 visitors prevented oversized owned field allocations but still
allowed parser scratch for escaped strings. The round-2 follow-up below removes
that gap using the reviewed #363 raw-token helper.

The #363 P3 compatibility fixes are also included: omitted StarterStatus
`reason`, `channel_id` and `funding_txid` decode as `None`; config loading rejects
an effective advertised Lightning address above 262 bytes with a field-specific
error, including the listening-address fallback.

escaped strings, omitted optional keys, nested fields, fixed-hex allocation

## PR #366 round 1 — global raw string ceiling and safe diagnostics

The Opus review of `4e0b9304` found that the declared-field bounds did not
cover strings supplied where serde expected scalars, structs or unit contents.
Serde formatted those strings into type errors before the wire layer copied
the error. An escaped unknown field name also allocated parser scratch and
was accepted, so it did not consume the invalid-frame budget.

`Frame::from_bytes` now extends the existing allocation-free depth preflight
with a **393,216-byte raw ceiling on every string token**, including keys,
ignored fields, enum contents and wrong-type values. The count excludes the
two delimiter quotes, includes every escape byte, and rejects as soon as it
exceeds the limit, even in an unfinished token. Escaped quotes/backslashes do
not end a token. Error text is fixed and contains no peer bytes. Serde is never
called for an over-limit token, so these failures use the existing invalid-frame
budget and ban path. The outer frame limit remains 16 MiB.

The ceiling is `6 * MAX_BOLT11_BYTES`: the largest declared strings are 64 KiB
BOLT11 and SDP fields, and a `\uXXXX` escape uses at most six raw bytes per
decoded UTF-8 byte (surrogate pairs use twelve raw bytes for four decoded
bytes). Fully escaped maximum-length legitimate fields therefore still fit.
Ciphertext and ratchet payloads are byte arrays. The narrower decoded field
limits remain enforced independently. This bounds individual string scratch
and serde type-error construction; it is not a claim that an entire frame
allocates at most 393,216 bytes or that below-ceiling errors allocate nothing.

Wire decode errors returned to callers use fixed text instead of copying the
serde error. Handshake decode failures likewise expose only `log_category()`.
Disconnect, MessageReject and InvoiceError log reasons strip control characters
and Unicode line/paragraph separators, and truncate on UTF-8 boundaries within
1,024 bytes. The same helper covers downstream node reason logs, legacy
CallEnd logging and Disconnect reasons returned by federation handshakes;
original control-event and WebSocket reasons are preserved. Relay register,
ack, deposit, drain and nested-envelope parse
failures send fixed rejection codes instead of reflecting serde error text;
these rejects round-trip under the receiver's 1 KiB reason cap.

The counting-allocator matrix covers u64/u32/u16/u8, bool, f64, optional u64,
Hello.version, price values, quote expiry, envelope timestamp/kind/payment
amount, root/nested unit and enum contents, struct/envelope bodies, ignored
values and unknown keys. Plain, escaped, multibyte and surrogate-pair inputs
are built before measuring, at one byte over the ceiling and near the 16 MiB
frame limit. Every case must fail with the fixed ceiling error, with no single
allocation over 4 KiB and no cumulative allocation over 16 KiB. Separate tests
preserve exact raw boundaries, maximum fully escaped BOLT11/SDP fields and
multiple adjacent tokens. Existing field-allocation probes now use 128 KiB
payloads, below the global ceiling, so the global guard cannot mask removal
of a narrower field guard. Fixed-hex probes additionally include 48 KiB of
fully escaped decoded data (288 KiB raw), so the global ceiling cannot mask
removal of the hex-specific pre-copy checks.

Transport tests exercise both wrong-type strings and previously accepted
escaped unknown keys through encrypted connections and require invalid-frame
bans. Diagnostic tests cover returned decode errors, encrypted handshake
errors, reason sanitization and relay rejection round-trips. The mutation
runner adds `frame.raw_string_ceiling`, which removes the length check while
retaining the other protections; `--only frame.raw_string_ceiling` selects it.
