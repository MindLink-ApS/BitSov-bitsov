## Medium — fixed in this PR

### M1 — Download notes still accept a signature that is not field 10

`scripts/release-sign.sh` accepts a signature only when `[GNUPG:] VALIDSIG` field 10 is `B299274C200301714DC6F51A7C2D6F8AC842EF6E`. That has been true since #342. The download side had no script that applies the same predicate.

`docs/releases/v0.3.0-rc10.md` through `v0.3.0-rc14.md` still tell an operator to `curl` `RELEASE_KEY.asc` from mutable `main` into a GnuPG home, then run `gpg --status-fd 1 --verify` and `shasum -a 256 -c`. The checkbox under each block is satisfied when verify exits 0 and the status text contains `GOODSIG` and `VALIDSIG` plus the fingerprint, and does not contain the expired or bad markers. A user id can contain that text. `gpg --fingerprint B299274C200301714DC6F51A7C2D6F8AC842EF6E` still exits 0 when the real key is in the same keyring, including when `RELEASE_KEY.asc` on `main` also carries a second key. Those five notes are historical checklists for unpublished candidates. They were still the only copy-paste verifier in the tree. `v0.3.0-rc19.md` and `RC_CHECKLIST_TEMPLATE.md` describe field 10 in prose and do not check it.

**Exploit sketch.** `RELEASE_KEY.asc` on `main` contains the release key and one other key. That other key's user id is the text `VALIDSIG B299274C200301714DC6F51A7C2D6F8AC842EF6E`. Someone signs a `SHA256SUMS` of attacker binaries with the other key. An operator runs the rc14 block. The fingerprint command prints the real key. `gpg --verify` exits 0. The status contains the fingerprint string and none of the rejected markers. `shasum -c` reports OK. The operator installs those binaries. The release-signing script would not have produced that signature. The old notes would have accepted it.

**Fix.** `scripts/verify-release.sh <download-dir> <release-public-key.asc>` reads the key file with `gpg --show-keys`, requires exactly one primary key, and requires its fingerprint to be the release key before importing it into a temporary GnuPG home. It does not fetch the key or the binaries, and it does not touch the caller's keyring. The signature predicate is the same function as `release-sign.sh`; `scripts/test-verify-release.sh` diffs the two copies. `SHA256SUMS` must name the five CLI binaries and may also name their `.sha256`, `.sbom.spdx.json`, and Darwin `.toolchain.txt` files. Every named file must be present, must be a regular non-symlink, and must match its hash. Another file, a directory, or a path outside the directory is refused. The five historical blocks now say not to run them and point at this script. The commands themselves stay as the record of what those candidates said. `docs/ops/RELEASE_POLICY.md`, `docs/releases/RC_CHECKLIST_TEMPLATE.md`, and the Linux install steps in `docs/operations/home-node.md` use the script. `git verify-tag` stays a separate check. The script does not decide whether a target was rebuilt.

`scripts/test-verify-release.sh` generates a throwaway ed25519 key and a second key whose user id contains `VALIDSIG` plus the first fingerprint. It rejects that user-id spoof, an `EXPKEYSIG` line, a tampered binary, an extra file, a symlink, a nested directory, a `../` name in the sums, a signature from the other key, and a substituted public key. The production script refuses the throwaway key. The shipped fingerprint constant is not edited.

## Low — fixed

### L1 — User unit did not set a private umask

`docs/operations/bitsov.service` sets `UMask=0077`. `docs/operations/konsensus.service` did not. A user manager often uses umask 022, so files the process creates and does not chmod are mode `0644`. `restrict_data_dir` (`crates/konsensus-node/src/main.rs:710`) forces the data directory to `0700` through `ensure_owner_private_dir`, and `write_protected` (`crates/konsensus-api/src/pairing.rs:4430`) writes secrets at `0600`. Another uid cannot open those files through the data directory. Files created outside that directory, or created before the chmod, follow the process umask. The same uid can read them either way.

**Fix.** The user unit sets `UMask=0077`. That changes creation mode only. The unit does not share files with a group. The verifier test requires the line in both units.

The host rebuild still refuses to treat a CI binary as verified until the local hash matches, unless the operator passed `--accept-unverified-host` with a reason. Non-host targets still need their own `--accept-unverified-target`. The script never publishes.

**I4 — Lockfile.** `Cargo.lock` is unchanged since `edb1839`. This pass did not re-fetch the advisory database and did not bump dependencies.
