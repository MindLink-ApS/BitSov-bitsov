## Medium — fixed in this PR

### M1 — PostgreSQL startup applied a schema newer than the binary

`PostgresStorage::apply_pending_migrations` (`crates/konsensus-storage/src/postgres.rs`). The runner walks the migration list compiled into this binary and skips versions already recorded in `_konsensus_migrations`. A recorded version that is not in that list was never read. Startup then succeeded. SQLite uses sqlx's migrator, which refuses that database with `VersionMissing`. The rc20 upgrade note and the migration 037 note, both added after the 2026-10-26 review, described the gap: PostgreSQL starts on the newer schema.

rc20 is the first release in this range whose schema the downgrade fence has to cover. Migrations 035, 036, and 037 add call-block state, the unpaid notice, and the invoice-hash binding the payment gate trusts. An older PostgreSQL binary that starts on that schema does not know those tables. The rc20 checklist tells the operator SQLite will refuse and PostgreSQL will start, which is the opposite of a fence.

**Fix.** `unknown_applied_migrations` returns the recorded versions this binary does not know. `refuse_future_schema` runs at the start of `apply_pending_migrations`, before any migration statement, and returns `StorageError::FutureSchema`. The error names version numbers and the highest version this binary knows. It does not include a connection string. `postgres_refuses_a_schema_newer_than_this_binary` locks the predicate, including call-block versions 35 through 37. The rc21 upgrade section, the migration 037 section, and the rc21 checklist now describe the fence. The rc20 checklist is left as the record of the rc20 binary, which does not contain this check. No migration file was edited.

## Low — left open

### L1 — rc20 and rc21 still describe signature verification in prose

`docs/releases/v0.3.0-rc20.md` and `docs/releases/v0.3.0-rc21.md`, section 3. Each checklist says to verify `SHA256SUMS.asc` with "the same primary-key check" as `git verify-tag`, then run `shasum -a 256 -c SHA256SUMS`. Neither names `[GNUPG:] VALIDSIG` field 10. Those two files did not exist at `323be6f`, so draft PR #447 does not edit them. The copy-paste blocks in rc10 through rc14, and the offline verifier that checks field 10, stay in that draft.

**Fix (not applied).** Point section 3 of rc20 and rc21 at `scripts/verify-release.sh` when #447 lands, or name field 10 in those checklists. This PR does not add a second verifier.

### L2 — The signet quickstart's Esplora clients follow redirects and buffer the body

`docs/QUICKSTART-SIGNET.md` (new in `#416`) sets `[lightning] esplora_url` and `[chain] api_url` to public HTTPS Esplora endpoints. `EsploraProvider::with_fallbacks` (`crates/konsensus-chain/src/esplora.rs`) builds a `reqwest` client with a timeout and no redirect policy, so the default policy follows redirects. `get_parsed` then reads `response.text()` with no byte cap. `probe_esplora_fee_estimates` (`crates/konsensus-lightning/src/ldk.rs`) does the same for the startup probe. LDK's own client (`vendor/ldk-node/src/chain/esplora.rs`, `esplora_http_client_builder`) sets a timeout and no redirect policy. The bitcoind RPC client and the bearer token client already use `redirect::Policy::none`.

A configured endpoint that answers with a redirect chooses the next host and scheme. The body is buffered for as long as the timeout allows. Rapid Gossip Sync's `reqwest::get` remains the 2026-10-26 I2 note; RGS is still off unless the operator sets it. The 2026-10-20 L3 note, that an Esplora URL may be `http`, is unchanged.

**Fix (not applied).** Use a redirect policy that stays on the configured host and on `https`, and stop reading after a fixed byte cap. The cap has to fit an Esplora transaction body, and the policy has to match the URLs the quickstart names. That is a client change, not a one-line edit. This PR does not change those clients.
