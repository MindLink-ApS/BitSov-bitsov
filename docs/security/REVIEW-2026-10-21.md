### H1 — Release-key check matched status text, not the VALIDSIG fingerprint

`scripts/release-sign.sh:24` (`signed_by_key`). Before this PR the predicate was an unanchored `grep` for `VALIDSIG $KEY_FPR` over the whole `gpg --status-fd` / `git verify-tag --raw` blob, plus a reject list for `EXPKEYSIG`, `REVKEYSIG`, `EXPSIG`, `BADSIG`, and `ERRSIG`.

GnuPG 2.4.4 prints the signer user id on `GOODSIG`. A key whose user id is `VALIDSIG B299274C200301714DC6F51A7C2D6F8AC842EF6E` produces:

```
[GNUPG:] GOODSIG <their-keyid> VALIDSIG B299274C200301714DC6F51A7C2D6F8AC842EF6E
[GNUPG:] VALIDSIG <their-fingerprint> ... <their-fingerprint>
```

Notation data does not carry this bypass: GnuPG percent-encodes the space (`VALIDSIG%20B299...`), so the old grep did not match a notation. The user id is printed with a literal space. There is no `BADSIG`. The old predicate returned success. Reproduced locally against the old function.

**Exploit sketch.** A writer who can push a tag signs `v0.3.0` with their own key and that user id, on a commit that is already on `origin/main`. The operator runs `scripts/release-sign.sh v0.3.0 <that-commit>`. The script says the existing tag is signed by `B299274C200301714DC6F51A7C2D6F8AC842EF6E` and does not replace it. It then detached-signs `SHA256SUMS` with the real release key. The published git tag is not signed by the release key. Anyone who stops at the script's check, or at `SHA256SUMS.asc`, treats the tag as release-key signed.

**Fix.** `signed_by_key` accepts only a `[GNUPG:] VALIDSIG` line whose signing fingerprint or primary-key fingerprint field is the release key, and still rejects the expired/revoked/bad markers. `scripts/test-release-sign.sh` case `notation` feeds the user-id spoof and requires rejection. Case `subkey` accepts a VALIDSIG whose primary field is the release key and whose signing field is not.

## Medium — fixed in this PR

### M1 — A draft can carry files the signature does not cover

`scripts/release-sign.sh:44` (`require_release_assets`). The signer used to download the five named binaries and their `.sha256` siblings and sign those hashes. It never listed the rest of the draft. Tag CI uploads those binaries, the checksums, and an SBOM per target (`.github/workflows/ci.yml` release upload, `files:` list). This repository does not build a DMG. Nothing stopped a `contents: write` job, or a second upload, from attaching `BitSov.dmg` or another installer beside the signed CLI binaries.

**Exploit sketch.** The draft is published with a valid `SHA256SUMS.asc` for the five CLI binaries and an extra disk image that is not in the sums. The GitHub release page offers the image as a download. A user who clicks it never reaches the signature check. The operator's script previously exited 0.

**Fix.** Before hashing, the asset name set must be exactly the five binaries, their `.sha256` files, and their `.sbom.spdx.json` files. `extra-asset` attaches `BitSov.dmg` and requires a refusal before download or signing. A missing SBOM fails the same way, which matches what tag CI already uploads.

### M2 — LND could report a settled payment as a smaller amount, and the grant gave the difference back

`crates/konsensus-lightning/src/lnd.rs:532` (`pay_invoice_with_fee_limit`) and `crates/konsensus-lightning/src/lnd.rs:400` (`reported_amount_msat`).

The router response's `value_msat` was parsed with `parse_u64`, which returns 0 for an empty, non-numeric, or out-of-range string (`lnd.rs` `parse_u64`). A missing `value_msat` on the pay path became amount 0. Status and list paths did `value_sat * 1000`, which wraps in release and panics in debug once the satoshi value exceeds `u64::MAX / 1000`. Channel capacity used the same multiply (`lnd.rs` list channels).

`resolve_payment` (`crates/konsensus-api/src/handlers/payments.rs:530`) settles a metered grant at `details.amount_msat` when status is `Settled`. `Budget::resolve` (`crates/konsensus-api/src/spend_budget.rs:781`) subtracts `reserved - actual` from `used_msat` when the reported amount is smaller. An explicit fee of 0 is a known fee, so a settled 0 or 1 msat with `fee_msat: "0"` returns almost the whole reservation. The invoice was already paid at its real amount. The paired caller can spend that grant again.

**Exploit sketch.** A paired token with a budget pays a 10_000 msat invoice through LND. The node POSTs `/v2/router/send` and LND settles it. The last stream line is `SUCCEEDED` with `value_msat` omitted or set to `"1"` and `fee_msat` `"0"` (a partial update, a proxy that drops the field, or a backend that lies about the figure). The API returns success for 0 or 1 msat. The grant's used total drops by the reserved principal and fee. A second invoice spends the grant again. The wallet already paid the first one. The same wrap on `value_sat` made a huge satoshi string look like a small millisatoshi amount on later status reads.

**Fix.** A settled pay requires `value_msat` to parse as an integer equal to the invoice amount. Anything else is `LightningError::Backend`, which `resolve_payment` does not release (`payments.rs:541`). In-flight results with no amount use the invoice amount, not 0. Status and list paths refuse a settled 0 and use `checked_mul` for satoshis. Channel capacity and the balance sat fallback use the same multiply. `settled_payment_without_matching_amount_is_not_zero` and `settled_amount_rejects_zero_and_satoshi_overflow` cover it.

A status lookup that returns a positive `value_msat` other than the invoice amount is still trusted, because that call does not have the invoice. The dispatch path, which is what releases the grant, no longer is.

## Medium — open

### M3 — Signed checksums are a snapshot of a mutable draft

`scripts/release-sign.sh:93` downloads each asset, hashes it, and later uploads `SHA256SUMS`. The draft stays writable by anyone with `contents: write`, including the tag CI job. This PR re-checks `isDraft` after the download and before signing (`release-sign.sh:104`, case `published-late`), so a release that flipped public during the hash is not then modified. It does not pin GitHub asset ids or digests.

**Exploit sketch.** After the operator's hash matches, a second upload replaces `bitsov-linux-x86_64` with other bytes and a matching `.sha256` under the same name. `SHA256SUMS.asc` still describes the bytes the operator downloaded. A later downloader who checks the signature sees a mismatch. A downloader who does not check the signature installs the replacement. Re-checking the draft flag does not close that. Rebuilding on the signing machine (the unmerged H3 recommendation) also does not, unless the rebuild is compared again to the objects still attached at publish time.

**Fix (not applied).** Record each asset's API digest, re-download immediately before `gpg --detach-sign`, and refuse to upload if the bytes moved. After publish, re-download once more and treat a mismatch as a failed release, not as a user problem. That is a larger change to the offline test double than this pass.

### M4 — No downgrade check before a tag is signed

`scripts/release-sign.sh:54` accepts any `vX.Y.Z` or `vX.Y.Z-rcN` that points at a commit on `origin/main`. It does not compare that version to the newest published release. This repository has no auto-updater and does not fetch DMGs or release URLs at runtime. GitHub's Latest release is the most recently published stable tag, not the highest version.

**Exploit sketch.** An operator (or the H1 tag path) signs and later publishes `v0.1.0` after `v0.3.0` is current. Clients and installers that follow GitHub Latest move backward. Checksums on the old tag can still verify. Nothing in this repo installs that tag by itself.

**Fix (not applied).** Refuse a stable tag that sorts below the newest published stable tag unless the operator passes an explicit downgrade flag. Keep rc tags comparable only within their base version. Do not invent a client updater here.

## Low

### L1 — On-chain send and keysend retries are not idempotent

`POST /api/v1/payments/send-onchain` (`crates/konsensus-api/src/handlers/payments.rs:1142`) has no operation id. Owner keysend (`payments.rs` `KeysendRequest`) uses `request_id` only for a metered debit. Channel open has an optional `operation_id` (`payments.rs:892`); omitting it still opens again.

**Exploit sketch.** The client times out after the node has broadcast, and sends the same body again. The second call is a second payment. A metered invoice pay is safer: LND and LDK refuse a payment hash they have already seen. Keysend and on-chain send mint a new spend each time.

**Fix (not applied).** Require a client operation id and store the outcome before broadcast, the way channel open already can. That needs a new table. This pass does not add a migration, and `payments.rs` is already edited on unmerged #337.

### L2 — LNbits balance multiply can wrap

`crates/konsensus-lightning/src/lnbits.rs:519`. `balance` is `i64`. `balance * 1000` panics in debug and wraps in release when the magnitude exceeds `i64::MAX / 1000`. A negative result is then clamped to 0. LNbits `pay_invoice_with_fee_limit` is the trait default, which refuses before dispatch, so this path does not pay. It can blank or crash a balance read.

**Fix (not applied).** Use `checked_mul` and return a backend error. Left out so this PR stays on the two paths that move or attest funds.

## Info

- Tag CI still stages draft binaries with `softprops/action-gh-release@v2` and other actions referenced by tag, not by commit SHA (`.github/workflows/ci.yml`). A moved tag can change what gets uploaded. Pinning is a workflow change and is left to the open CI PRs.
- There is no in-process updater, DMG builder, or download URL. Update trust is the operator script plus the signed checksum file. H3 from the 2026-10-20 review (the signature does not prove a rebuild of the tag) is unchanged on main.
- An omitted `max_routing_fee_msat` is capped by `RoutingFeePolicy::ceiling` (`crates/konsensus-core/src/traits/lightning.rs:56`). The caller can tighten that cap and cannot widen it. The policy minimum can exceed a tiny principal; the metered debit reserves principal plus that fee, so it does not spend past the grant.
- `parse_u64` still maps garbage to 0 for non-amount fields (timestamps, the old balance msat string). Settled payment amounts no longer use it.
