# Direct payments: `POST /payments/pay` and `POST /payments/keysend`

Both routes pay from the node's own wallet on the owner API (`spend` scope,
metered for a paired client under its budget grant). Nodes advertising
`direct_payment_operations_v1` in `/api/v1/status` `api_capabilities` follow
this contract. Two properties hold on every path: nothing is reported paid
before the backend reports it settled, and nothing is dispatched twice under
one `request_id`.

## Request

| Field | `pay` | `keysend` |
| --- | --- | --- |
| `request_id` | **required**: 1–128 printable ASCII bytes without spaces, generated by the client before the first attempt and repeated unchanged on every retry | same |
| `bolt11` | the invoice, with an amount | — |
| `dest_pubkey` | — | 33-byte hex node key |
| `amount_msat` | — | at least 1 sat |
| `memo` | — | optional |
| `max_routing_fee_msat` | optional ceiling (see [ALL-IN-FEE-CAPS](ALL-IN-FEE-CAPS.md)) | same |

A missing or malformed `request_id` is `400` with the remedy in `error`;
nothing is looked up, debited or dispatched. The id is recorded in the node's
encrypted operation ledger (the same store `open-channel` and `send-onchain`
use, keyed `pay:<request_id>` / `keysend:<request_id>`) **before** any budget
debit or backend call. Ids are per route: the same string names different
operations on `pay` and `keysend`. Within a budget grant the id is also still
consumed once, as before ([SPEND_BUDGET_GRANTS](../SPEND_BUDGET_GRANTS.md)).

## Status codes

| Code | `status` | Meaning |
| --- | --- | --- |
| `200` | `settled` | The backend reported the payment settled. `preimage` is the proof; `fee_paid_msat` is the actual LDK routing fee (omitted on other backends). Only this response means paid. |
| `202` | `in_flight` | Dispatched but not final after a short settlement wait (about 3 s), or the first attempt's outcome is not recorded yet. `payment_hash` (empty only for a keysend the backend has not yet identified) and `operation_id` are returned; `preimage` is empty and `fee_paid_msat` absent. Repeat the request with the same `request_id`, or poll `GET /payments/{payment_hash}`. |
| `400` `not_dispatched` | — | Refused before anything left (fee ceiling, local validation, backend refusal). The id is freed and may be retried. |
| `409` `operation_mismatch` | — | The same `request_id` with different parameters. Nothing is dispatched; use a new id for a new payment. |
| `502` | — | A positive backend failure after dispatch (`"… payment failed before settlement"`), or an ambiguous backend error. |
| `503` `not_ready` | — | The wallet is not money-ready. Saved receipts still answer. |

Every response keeps the pre-existing fields (`payment_hash`, `amount_msat`,
`preimage`, `max_routing_fee_msat`, `fee_paid_msat`) and adds `status`,
`request_id`, `operation_id` and, on an answer served from the record,
`replayed: true`. The `keysend` route's `status` values are now the lowercase
`settled` / `in_flight` of this table (previously the backend's `Debug` name,
such as `Settled`).

## Retrying with the same `request_id`

A repeat never dispatches. What it answers depends on what is recorded:

| Recorded | Repeat answers |
| --- | --- |
| settled | `200 settled`, `replayed: true`, the original proof |
| positive failure | the same `502`; a failure is bound to its id |
| in flight (hash known) | the backend is read by hash: settled → `200` (and the record is finalized); failed → `502`; otherwise `202 in_flight` |
| ambiguous error, or the first attempt not yet recorded | `202 in_flight`, with `last_error` when one was recorded; for an invoice the backend is read by hash as above |

A settled or failed record is final and immutable. Every outcome write is
fenced on the row it was derived from (request binding, insertion time and
state): a retry whose row was freed by a refusal and re-created for another
request under the same id writes nothing and answers `409`. An in-flight or
ambiguous record is finalized only from what the backend reports for the
**outgoing** payment under that hash; an incoming record under the same hash (a
self-payment's invoice) is never taken as settlement. Elapsed time and a
missing backend record are never evidence of non-dispatch: a keysend whose
backend reply was lost before a hash was recorded stays `202` under its id.
Inspect `GET /payments` before choosing a new id for it.

## Budget accounting

A metered caller's reservation is settled on `200`, released on a refusal
before dispatch or a positive failure, and otherwise kept reserved (the
unknown outcome of [SPEND_BUDGET_GRANTS](../SPEND_BUDGET_GRANTS.md)). A `202`
keeps the reservation; it is not released by a later `200` replay.

## Compatibility

Clients that treated `200` as paid were correct only by luck: before this
contract both routes returned `200` with an empty `preimage` while the payment
was still in flight. The breaking changes are: `request_id` is required
(`400` without it), an in-flight payment is `202` instead of `200`, a keysend
that the backend reports failed is `502` instead of `200` with
`status: "Failed"`, and `keysend`'s `status` strings are lowercase. Gate the
new handling on the `direct_payment_operations_v1` capability.
