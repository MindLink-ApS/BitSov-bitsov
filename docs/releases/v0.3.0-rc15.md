### Lightning security stack and operator actions

- **Vendored Lightning 0.2.2 → 0.2.7.** Includes the funds-theft fixes
  **#5057** (acknowledged commitment rollback during channel reestablishment)
  and **#5042** (underfunded LSPS2 forwards), plus **#4867**, the Electrum
  script-history amplification DoS fix. The lockfile also selects
  `lightning-liquidity` and `lightning-transaction-sync` 0.2.7,
  `lightning-background-processor` 0.2.3 and `lightning-types` 0.3.5.
  The LSPS2 fix needs both Lightning and liquidity changes; the Electrum fix
  is in transaction-sync and applies to the Electrum backend. Existing local
  patches are retained. See [provenance and applicability](../security/ldk-0.2.7/README.md).
- **Selected ldk-node 0.7.1 backports; vendor remains 0.7.0.** **#1032**
  creates a fresh ChannelManager only on `NotFound`; other store read errors
  now fail closed with `BuildError::ReadFailed`. **#899** rejects nonzero fee
  skims on unregistered receives, including keysend and BOLT12. **#1157**
  rejects unknown required (even) custom TLVs before exposing claimability,
  including manual claims. **#1035** removes the preimage from successful-send
  logs; payment receipts and application events still contain it. This is not
  a full ldk-node 0.7.1 upgrade. See [backport evidence](../security/ldk-node-0.7.1/README.md).
- **possiblyrandom 0.2.1.** All three lockfiles select 0.2.1, which enables
  OS entropy on supported targets without requiring an explicit `getrandom`
  feature. This fixes the default-feature zero-buffer path in 0.2.0; it is
  not a guarantee of entropy on unsupported targets or OS failure.
- **Late-failure and circular-payment fixes.** A late `PaymentFailed` after
  a successful outbound Lightning payment preserves the complete receipt and
  emits no contradictory application failure event. An inbound HTLC using
  an outbound payment hash is still rejected, but no longer marks that
  outbound payment failed. Genuine outbound failures still use `PaymentFailed`.
  These are the 0.7.1 release backports, including the circular-payment part
  of #1157; they do not establish a general concurrent-writer guarantee.
  See [payment-status evidence](../security/ldk-node-0.7.1/PAYMENT-STATUS.md).

**No downgrade to rc14 after running rc15 with embedded LDK.** Lightning
0.2.7 writes new optional persisted fields that 0.2.2 skips and drops on
reserialization; being able to decode state does not make downgrade safe.
The existing LDK rollback rule already forbids it. Keep the latest state and
roll forward. The reviewed cutoff and narrow pre-LDK failed-start restoration
procedure below remain in force; unchanged generation 3 is not permission to
downgrade.
A `ReadFailed` / "Failed to read channel manager from store" start always
occurs after storage has opened and migrations have run, past step 8's
cutoff, so it never qualifies for this exception and you must never restore
the pre-swap backup because of it.

**New fail-closed startup error:** the LDK log `ldk_node.log` in the storage
directory reports
`Failed to read channel manager from store: <error>`; the builder returns
`BuildError::ReadFailed`, surfaced by BitSov as
`lightning backend error: failed to build LDK node: Failed to read from store.`
The latter is a general
store-read error, so inspect the accompanying log to identify the manager.
Stop and preserve the latest state; diagnose storage availability, permissions
or corruption. **Do not delete or replace the ChannelManager to "fix" it**,
including by copying one from an older backup or initializing fresh state.
That can turn an error into `NotFound` or stale channel state and risk funds.

**Hub LSPS2/JIT caveat:** HTLCs already queued by the old LSPS2 code retain
their unchecked amounts. Drain or inspect those pending JIT flows before
relying on the fix for them; restarting/upgrading does not retroactively
validate the queue. No deployed hub queue was inspected in this preparation.

Release boundaries that must remain explicit:

- **Owner-device enrollment (#301).** An already enrolled owner device can
  issue signed, five-minute, single-use pairing tickets over its own Noise
  session while unlocked in `--local-owner-device` mode (including `--home`).
  Issuance is limited to five tickets per rolling 15 minutes node-wide;
  consumption rechecks the issuer's authority. Owner-only pending SAS reads
  and v2 delegation preserve claim, possession, epoch and owner-attestation
  checks. This needs client QR/approval UI support; a paired token alone
  cannot enroll an owner. See [device keys](../security/device-keys.md#adding-a-device-over-the-noise-tunnel).
- **Encryption passwords (#302).** Empty or whitespace-only new encryption
  passwords fail before mnemonic-file writes in init, restore, seed encryption
  and encrypted bootstrap. Interactive encryption input is hidden. Existing
  plaintext and encrypted files remain readable; upgrading does not encrypt
  a plaintext seed. See [password input](../operations/password-input.md).
- **Owner approvals (#303).** `owner_device_approval_v1` adds bounded
  `spend_grant` and one-use `first_contact` requests. Only a different pairing's
  enrolled owner device, with its own token and matching authenticated Noise
  session, may sign the exact node-rendered terms. Requests grant no authority;
  current epochs, expiry, live grant bindings and single-use consumption are
  checked. Pending approval requests do not survive restart. Apps must implement
  the approval flow; console approvals remain available. See
  [owner approvals](../v2/OWNER-APPROVALS.md#owner-device-approvals-v1).
- **Approval readiness.** For an owner-console start, use an encrypted seed,
  no adjacent plaintext `.txt` copy, and type its password at startup.
  `GET /api/v1/pair/device-keys` reports `device_approvals` as
  `seed_not_encrypted` or `seed_password_not_typed` when those requirements fail.
  Capability flags alone do not mean approvals are enabled. The code also
  permits descriptor passwords and authenticated remote unlock with explicit
  `--local-owner-device` authority (`--home` includes it); `--password` and
  `--password-file` do not qualify. Invalid explicit local-owner starts refuse
  startup. See [the upgrade readiness check](../UPGRADING.md#rc14--rc15-procedure).
- **Breaker reset (#304).** `owner_device_approval_breaker_reset_v1` enables
  `breaker_reset` by an independent owner device. A paused pairing cannot
  reset itself, even with its own enrolled owner key. The owner signs the
  node's grant/breaker/remaining-budget snapshot; changed state invalidates
  that snapshot. At most three successful device resets per grant per rolling
  86,400 seconds survive restart. Reset clears rolling history, failure streak
  and pause, but preserves spent budget, pending/unknown reservations, payment
  dedupe, expiry and payee restrictions. It cannot make an uncertain payment
  safe to repeat. Console reset authority remains unchanged.
- **Pairing v7 (#304).** v2–v6 stores migrate on write to
  `pairing/clients.json` v7, retaining reset history/generation and rolling
  refusal evidence. rc14 supports only up to v6 and refuses v7. There is no
  reverse migration: do not lower the version or remove security fields.
  For a v7 file, **do not follow rc14's refusal hint “remove the file to
  re-pair from scratch”**; preserve `pairing/clients.json` and use rc15.
- **Operation abandonment (#306).**
  `POST /api/v1/messages/operations/{id}/abandon`, advertised by
  `message_operation_abandon_v1`, serializes with compose. Unused IDs and
  prepared/released operations proven unpaid become durable tombstones;
  late compose returns `operation_abandoned`. Payment/admission journal and
  wallet evidence gate abandonment. HTTP 409 returns the current receipt,
  including on repeat abandonment; inspect its state before continuing.
  Recovery releases proven-unpaid linked budget and orphan call reservations
  without reopening abandoned IDs, and compaction retains replay protection.
  This is not cancellation or refund of a dispatched payment. See
  [durable operations](../v2/EXACTLY-ONCE-OPERATIONS.md#abandoning-an-unused-operation-id).
- **Migration 029 and rollback (#306).** `029_operation_abandon.sql` adds the
  `abandoned` state and retention support in SQLite and PostgreSQL. SQLite
  rebuilds the table, copying receipt metadata, versions and opaque recovery
  bytes. The migration is forward-only. Leave `KONSENSUS_SQLITE_MIGRATIONS_DIR`
  **unset** so the binary uses embedded migrations; a stale override missing
  029 refuses startup. Rollback requires restoring the coherent **pre-swap
  backup together with the rc14 binary**, never rc14 against upgraded storage.
  For embedded LDK, **treat LDK as started and never restore the pre-swap
  backup** if rc15 ever reached `UNLOCKED`, ever started with a descriptor
  (`--password-fd`) or `--home` password, migration 029 is recorded as applied,
  or you cannot tell. Check the actual live SQLite database file (resolved
  from `[storage].path`, not a connection URL or the backup) read-only:

  ```sh
  sqlite3 -readonly /absolute/path/to/live/database.sqlite 'SELECT version FROM _sqlx_migrations WHERE version = 29 AND success = 1;'
  ```

  `29` closes the rollback window; no row/error alone does not prove safety.
  In all four cases **keep the latest state and roll forward**. Restore only
  if none applies and rc15 stopped while `LOCKED` or failed before storage
  opened. Storage opening applies 029 immediately before Lightning provider
  construction. Descriptor starts skip the remote `LOCKED` wait; `--home`
  waits for remote unlock before construction. After the first rc15 unlock
  (or another cutoff), rename the pre-swap backup's `ldk/` to
  `ldk.STALE-DO-NOT-RESTORE/` or quarantine it with a dated note: “Stale after
  rc15; never restore or run this channel state; keep latest state and roll
  forward.” Do not rename the live `ldk/`. The generation-3 and host/volume
  fences are not proof that a historical channel store is safe.
- **Dependencies (#307).** The committed lockfile contains `quinn-proto`
  0.11.18 and its updated transitive dependencies. The PR identifies this as
  a security-advisory update; this preparation does not claim a fresh advisory
  scan or a vulnerability-free dependency tree.

in the local GnuPG keyring, `gh` has push rights to `MindLink-ApS/BitSov-bitsov`,
and `<sha>` is the final rc15 release commit on `origin/main` recorded above.


`<sha>`, downloads all five draft binaries and verifies their `.sha256` files,
