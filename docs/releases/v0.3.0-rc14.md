Release boundaries that must remain explicit:

- rc14 is the first release with grant breakers; the app's separate AI pairing
  (#195) depends on it. This release does not ship that app feature.
- New grants default to 10 attempts/minute, 60/hour, 5 consecutive failures and
  1,000 sats/10 minutes. New relation grants have these fixed limits shared
  across envelopes; a larger envelope cannot widen them. Console approval may
  choose other positive limits. Legacy grants without fields keep `u64::MAX`
  limits until explicitly replaced; envelope renewal preserves them.
- Pairing file v6 is forward-only; rc13 refuses it. Preserve the current store
  and roll forward. Existing generation-3 and copied-state/recovery fences
  remain in force. The host/volume fence cannot prove freshness or detect every
  same-host SD-image rollback. Never start a historical LDK store.
- Failure pause needs owner-console reset; time, renewal or restart cannot
  unpause it. Reset does not refund budget, clear dedupe or resolve unknown
  payments. There is no paired-app reset authority.
- `konsensus recover` is owner-console-only maintenance for embedded LDK,
  with a reachable original hub that closes from its state. The encrypted SCB
  is an index only. Confirmed sweeps, an externally funded fresh LSPS2 channel,
  a settled 1-sat hub payment and a final chain recheck precede completion.
  An unreachable hub has no backup force-close fallback. HTLCs/legacy non-v2
  keys are outside scope; a seed-only scan cannot prove all channels closed.
- Recovery state in owner status is read-only. Maintenance serves no API;
  public health and non-owner status do not expose recovery state.
- CLN remains a preview that **cannot pay**, even with #297. Receive/read does
  not enable outgoing invoice payments or keysend; payment capability and
  money readiness stay false. CLN owns its funds and backups.
- The [test Pi procedure](../UPGRADING.md#test-pi-retained-rc13--rc14-upgrade)
  upgrades the retained rc13 home node. No wipe, recovery drill or Pi smoke
  result is claimed by this preparation.

## 2. Sign

Prerequisites: the release secret key is in the local GnuPG keyring, `gh` is
authenticated with push rights to `MindLink-ApS/BitSov-bitsov`, and `<sha>`
is the post-merge release commit recorded above, on `origin/main`, containing
#297 and this rc14 docs/version PR. Use the full SHA, not a pre-merge tip.

```sh
scripts/release-sign.sh v0.3.0-rc14 <sha>
```

The script:

1. Creates and pushes a signed `v0.3.0-rc14` tag on `<sha>`. If the tag
   already exists on that commit with a valid signature, it reuses it.
2. Waits for the tag's `ci.yml` push run. It requires that run to have built
   exactly `<sha>`, and stops if CI fails.
3. Downloads the five draft binaries (`bitsov-darwin-aarch64`,
   `bitsov-darwin-x86_64`, `bitsov-linux-aarch64`, `bitsov-linux-x86_64`,
   `bitsov-windows-x86_64`) and checks each against its `.sha256`.
4. Writes `SHA256SUMS`, signs it as `SHA256SUMS.asc`, verifies the signature
   and attaches both files to the **draft**. It never publishes.
