Release boundaries that must remain explicit:

- `konsensus recover` is not shipped. The new library does not scan or broadcast,
  is not wired into the node, and covers neither HTLCs nor v1 remote keys.
- The copied-state fence refuses host/volume mismatches, but cannot establish
  freshness or detect every copy; same-host SD-image rollback remains undetected.
  Generation 3 and pairing schema v5 are forward-only; do not downgrade markers
  or restore an old live store.
- Non-service embedded LDK nodes default to hub-only admission. An empty hub
  set refuses new channels; lockable starts cannot opt out. Caps do not change
  existing channels or provide active locked/offline protection from the hub.
- mDNS requires the `mdns` build feature and `--home`, with remote access
  configured and mDNS not disabled. Current tag CI does not enable the feature;
  default release artifacts must not be described as advertising mDNS.
- The physical claim code is **18 characters** (16 random base32 plus 2 checksum).
  Never shorten it. The four SAS words are a separate comparison, not the claim
  code or recovery phrase. App integration is separate; old clients cannot
  bypass SAS on a box that has a claim code.
- Empty-box remote first run requires `--home`; `--remote-unlock` alone or with
  `--local-owner-device` is insufficient. Finalize requires LAN page approval
  and provides separate identity-signed locked box and unlocked live pins.
- The test Pi will be wiped and set up fresh with the new onboarding, after its
  old funds/channels are safely resolved. The [Pi procedure](../UPGRADING.md#test-pi-planned-wipe-and-fresh-rc13-onboarding)
  is planned work, not evidence of a completed wipe or smoke test.

## 2. Sign

Prerequisites: the release secret key is in the local GnuPG keyring, `gh` is
authenticated with push rights to `MindLink-ApS/BitSov-bitsov`, and `<sha>`
is the post-merge release commit recorded above, on `origin/main`, containing
#287 and this rc13 docs/version PR. Use the full SHA, not a pre-merge tip.

```sh
scripts/release-sign.sh v0.3.0-rc13 <sha>
```

The script:

1. Creates and pushes a signed `v0.3.0-rc13` tag on `<sha>`. If the tag
   already exists on that commit with a valid signature, it reuses it.
2. Waits for the tag's `ci.yml` push run. It requires that run to have built
   exactly `<sha>`, and stops if CI fails.
3. Downloads the five draft binaries (`bitsov-darwin-aarch64`,
   `bitsov-darwin-x86_64`, `bitsov-linux-aarch64`, `bitsov-linux-x86_64`,
   `bitsov-windows-x86_64`) and checks each against its `.sha256`.
4. Writes `SHA256SUMS`, signs it as `SHA256SUMS.asc`, verifies the signature
   and attaches both files to the **draft**. It never publishes.
