## Paid-call behaviour and known limits

A paid call now ends when the callee's app connection is lost, including a
brief network interruption, instead of continuing to charge. Reconnecting the
app does not resume a call ended by this cutoff. Reconcile the closing result
before starting another call.

**Update both nodes before paid calls.** This protection runs on the callee's
node and requires rc24 there. With an rc23 callee, the old behaviour remains:
a cut app connection can leave the call live and the caller can pay further
blocks. Do not run paid calls while versions are mixed. Upgrading only the
caller does not supply the callee-side cutoff.

**Restart:** a pending detach is not replayed after a restart. The regtest
restart observation below does not establish replay or a durable detach queue.

**Peer notification:** a media-drop hangup does not notify the peer. The peer's
node ends the call at the next refused renewal, about 65 seconds later.
That delay is separate from the callee's local closure. A brief interruption
can therefore end the call even if connectivity returns before the peer closes.

The [rc23 known limits](v0.3.0-rc23.md#known-limits) remain, including session
recovery and deferred-message reconciliation, the temporary SQLite applicability
waiver expiring on 2026-12-09, inbound connection saturation and chain-source
constraints. Retain existing operation IDs when resolving uncertain paid results;
do not create a new paid operation to clear an uncertain result.

## Wire, storage and compatibility

No new wire format, SQL migration, encrypted-record format or pairing-store
version is introduced since rc23. Pairing storage remains v8. Those unchanged
formats do not establish paid-call compatibility with an rc23 callee.

The forward-only storage changes inherited from rc23 still apply: migrations
033, 038 and 039 and the location-bound encrypted-record completion markers.
Keep current state and markers intact. Nodes coming from rc22 or earlier must
also follow [rc22 → rc23](../UPGRADING.md#rc22--rc23). Existing
[rollback constraints](../UPGRADING.md#rollback-constraints) remain.

## 4. Retained nodes: rc23 → rc24

These steps are for a future signed release. Rehearse on disposable regtest
data before a retained signet node, as in rc23 section 4.

1. Record the running binary/version, service command, configuration and data
   locations on both nodes. End calls and reconcile pending payments using
   their existing IDs. Stop only BitSov; leave separately managed Lightning
   backends alone. Do not run paid calls during the mixed-version interval.
2. Take a consistent backup of the complete BitSov data directory and, for
   PostgreSQL, its database. Retain config, wallet/channel, pairing, session
   and operation state together. A backup is not permission to rewind a live
   node after new state has been written.
3. Verify the future signed artifact for the correct platform, stage it beside
   the retained binary, and confirm `--version` reports `konsensus 0.3.0-rc24`.
   Resolve tier consistency and API bind settings. Review optional media
   settings and the configured chain source using `chain-tip`; do not change
   or accept a source implicitly.
4. Switch the BitSov binary and start with the retained config, data and normal
   owner controls. Do not re-run `init`. There are no new migrations since
   rc23. Earlier nodes must also complete rc23's migrations 033, 038 and 039
   and encrypted record upgrade under the forward-only recovery rules.
5. Inspect migration and aggregate record-upgrade logs. Keep all completion
   markers and investigate unreadable or unwritable data. Check owner
   `node_version`, health, identity, contacts, channels, chain source and
   `money_ready`; normal initial wallet sync does not establish payment
   readiness. Resolve `chain_unavailable` by restoring source availability
   and freshness before priced work. Repeat the upgrade on the other node
   and confirm both report rc24 before any paid call.
6. Read session state on both peers, then confirm one message in each direction
   on signet. Reconcile pending results before retrying. With both nodes on
   rc24, check a call and its closing result within the configured cap. A
   media-drop hangup does not notify the peer; allow about 65 seconds for
   its node to close at the next refused renewal. This is not real-hardware
   cutoff evidence until recorded. Keep the upgraded data intact.

## 5. Rollback and recovery

Prefer rolling forward with the latest complete state. No retained-node
rc24 → rc23 rollback rehearsal is recorded. Returning a callee to rc23 also
returns the old app-disconnection behaviour, so do not run paid calls while
versions are mixed. Before replacing an installed candidate, end calls,
reconcile operations and preserve the current complete state.

Do not downgrade data opened by rc23 or rc24 to rc22 or older. There is no
in-place reverse migration or encrypted-record downgrade. Keep migration rows
and completion markers. Released older PostgreSQL binaries may start despite
unknown migrations; that does not establish compatibility. SQLite refusal
also provides no downgrade path. Never restore an older database beneath newer
wallet/channel, pairing or ratchet state, or remove payment receipts to make
an old binary start. Any backup recovery crossing migrations 038/039 requires
a separately established consistent-state plan, including a pre-upgrade
`konsensus.db` on SQLite. PostgreSQL has no down migration either. Follow
[rollback constraints](../UPGRADING.md#rollback-constraints), preserve unresolved
operation IDs and repeat upgrade checks after a forward repair.

## Evidence

and synthetic media clients. Caller cut, callee cut and unanswered ring-out
closed within about 67 seconds without another settled media block. The
callee-restart case also closed without another block, but its renewal failed
before Lightning dispatch; it does not establish successful-dispatch refusal
after restart. Session-loss recovery retained the paid operation without a
second payment. The paid-call lane completed 4 scenarios and three-node E2E
completed 6; crate validation recorded 3,679 completed tests, zero failures,
24 existing ignored tests and Clippy with exit 0.

app connection was cut and settled one further media block. This is the known
