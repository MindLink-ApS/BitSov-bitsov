# BitSov v0.3.0-rc19.1 — operator signing checklist

**Pre-release.** Not for production use. rc19.1 = the rc19 tag (`e8ed5874`,
`v0.3.0-rc19`, never published) plus two cherry-picked release-tooling PRs: #355,
which pins the macOS release toolchain, and #358, which lets the signer accept
this dotted tag from its exact release branch. **No runtime code changes from rc19.** The rc19 draft
could not be signed: its darwin binaries were built in CI with Xcode 26.6
(17F113, SDK 26.5) while the signing host (NOVA) has Xcode 27.1 (27A9275,
SDK 27.0), so the H3 exact-tag host rebuild did not match. rc19.1 rebuilds the
same code with CI and the signing host on the same toolchain.

The tag is created on a release branch, not on `main`. `main` already carries
#356, #347, #350 and #338, which ship in rc20. This preparation does not sign,
tag or publish.

## 0. Tag (operator, under Rasmus's rc19 GO)

After both review PASSes name the same `<release sha>`, the operator (Atlas,
under Rasmus's rc19 tag-and-sign GO) creates and pushes the signed tag. Do not
move `release/v0.3.0-rc19.1` after the reviews: the signer requires the tag to
equal that branch's head exactly. Pushing the tag makes CI stage the unsigned draft:

```sh
git fetch origin release/v0.3.0-rc19.1
git tag -s v0.3.0-rc19.1 -m "BitSov v0.3.0-rc19.1" <release sha>
git verify-tag v0.3.0-rc19.1
git push origin refs/tags/v0.3.0-rc19.1
```

## 2. Dry-run gate, then sign (operator only)

- [ ] Run `scripts/release-sign.sh --dry-run v0.3.0-rc19.1` on the signing host (NOVA, Xcode 27.1) and investigate any darwin-aarch64 rebuild mismatch; never break-glass under time pressure.

**This gate precedes any real artifact signing.** The line above names the
required dry-run; the current script also requires `<release sha>` and an
explicit waiver for each non-host target. It requires an **existing signed tag**
and CI draft assets: it will not create a tag in dry-run mode. Thus an untagged
prep cannot yet complete this gate. Initial tag signing, which triggers CI,
is a separate operator prerequisite; it does not approve the CI binaries.
Do not use a normal signer invocation merely to get past this prerequisite:
it would continue toward artifact signing without the completed dry-run.
No tag or key operation is authorized or performed by this preparation.

For an Apple Silicon Mac (`aarch64-apple-darwin`), after the operator has
separately established the reviewed signed tag and draft, the full dry-run is:

```sh
scripts/release-sign.sh --dry-run \
  --accept-unverified-target x86_64-apple-darwin \
  --accept-unverified-target aarch64-unknown-linux-gnu \
  --accept-unverified-target x86_64-unknown-linux-gnu \
  --accept-unverified-target x86_64-pc-windows-msvc \
  v0.3.0-rc19.1 <release sha>
```

Each target waiver requires a separate operator decision and recorded rationale;
these flags are not evidence of an independent rebuild. If using a different
host, adjust the waivers to exclude that host. Follow the
[RC template](RC_CHECKLIST_TEMPLATE.md) and
[independent rebuild policy](../ops/RELEASE_POLICY.md#independent-rebuild-gate-h3).

- [ ] Confirm the tag resolves to `<release sha>`, which equals the head of
      `origin/release/v0.3.0-rc19.1` (the signer enforces this, #358), the CI build
      SHA matches, and the release is still a draft. Existing tags must have a
      valid release-key signature; never move or reuse the rc18, rc19 or rc19.1 tags.
- [ ] Confirm signature validation uses an anchored `[GNUPG:] VALIDSIG` record
      whose **field 10 after VALIDSIG (primary-key fingerprint)** is
      `B299274C200301714DC6F51A7C2D6F8AC842EF6E`. A matching GOODSIG user ID,
      signing-fingerprint field or trailing token is insufficient. Signing
      subkeys are accepted only with that primary fingerprint; expired,
      revoked and bad/error signatures are rejected (#342).
- [ ] Confirm exactly 17 source assets: five binaries (`bitsov-darwin-aarch64`,
      `bitsov-darwin-x86_64`, `bitsov-linux-aarch64`, `bitsov-linux-x86_64`,
      `bitsov-windows-x86_64`), each with `.sha256` and `.sbom.spdx.json`, plus
      `bitsov-darwin-aarch64.toolchain.txt` and `bitsov-darwin-x86_64.toolchain.txt`.
      `SHA256SUMS` must have **17 entries**, covering all of them. On a full or
      partial retry, only the exact extra names `SHA256SUMS` and
      `SHA256SUMS.asc` are allowed and regenerated; missing source assets,
      lookalike names and any other extras still fail (#342).
- [ ] Rebuild the exact tag commit in the detached worktree using its pinned
      toolchain and shared recipe. Confirm `VERIFIED` records the host, tag,
      commit and matching local/CI SHA-256. Archive command/output and every
      non-host `ACCEPT UNVERIFIED` entry with its rationale (#341).
- [ ] On mismatch, stop and investigate the printed `REBUILD EVIDENCE` directory
      under `release-sign-evidence/`: rebuilt binary, `host-hash.diff`,
      `SHA256SUMS` and `manifest.txt`. Evidence survives rejection/dry-run;
      retries retain separate directories. Never break-glass under time pressure.
- [ ] Only after investigation, if Rasmus explicitly accepts the host remaining
      unverified, supply `--accept-unverified-host "<incident-specific reason>"`.
      Archive `WARNING: BREAK-GLASS ACCEPT UNVERIFIED HOST`, exact tag/commit/
      target, **both hashes**, reason, evidence and command/output. This neither
      skips the rebuild nor waives build failures or other gates. These records
      are not automatically uploaded or signed; checksums still describe CI bytes.
- [ ] After the dry-run gate and review, Rasmus alone reruns the full command
      above **without `--dry-run`**, retaining the reviewed target waivers and
      adding a host reason only if explicitly approved after investigation.
      The signer rechecks draft status before accessing the release key,
      signs and verifies `SHA256SUMS`, then uploads `SHA256SUMS` and
      `SHA256SUMS.asc` with retry-safe replacement. It never publishes.

## 3. Verify independently before publishing

Use a fresh download directory and a throwaway GnuPG keyring importing the
reviewed `RELEASE_KEY.asc`, following the [release policy](../ops/RELEASE_POLICY.md).

- [ ] Verify `git verify-tag v0.3.0-rc19.1` against the pinned primary fingerprint
      above; `git rev-parse v0.3.0-rc19.1^{commit}` must equal `<release sha>`.
- [ ] Verify `SHA256SUMS.asc` with the same primary-key check, inspect the exact
      asset set and 17 manifest entries, then run `shasum -a 256 -c SHA256SUMS`
      over all five binaries, checksum files, SBOMs and the two darwin
      `.toolchain.txt` records. Check SBOM/provenance;
      the verified host binary reports `konsensus 0.3.0-rc19.1`.
- [ ] Re-download and verify the assets attached at publication time: a draft
      can change after the signer's download. Record all unverified targets
      (including the host if break-glass was used) as unverified.
- [ ] Rasmus approves publication as a pre-release. Re-pin the app only after
      publication and verification, following
      [rc15's app checklist](v0.3.0-rc15.md#5-app-re-pin-bitsov-app).

## 4. Beta nodes (bitsov-pi, Umbrel): rc18 → rc19.1

Only after publication and Atlas's go-ahead.

1. Record the current BitSov binary/version, config, data directory, service
   command and signet network. Reconcile pending channel opens/payments.
2. Check that the config parent is dedicated, owned by the node user and can
   be forced to 0700; check container volume ownership. Update argv-secret
   launchers to fd/file/prompt input. See [upgrade notes](../UPGRADING.md#rc18--rc19).
3. Verify the signed artifact for the node's OS/architecture; stage rc19.1 next
   to rc18 and confirm `konsensus 0.3.0-rc19.1`. Retain the latest data and seed;
   do not re-run `init` or restore a historical snapshot.
4. Stop only BitSov, switch its binary path, and restart with the retained
   config/data and intended owner-control/startup options. **Never stop,
   reconfigure or modify Umbrel's own LND or wallet.**
5. Check version, `/api/v1/health`, node identity, contacts/channels and signet
   status/funding address. Verify the encrypted-seed owner-token flow, local
   Host/Origin behavior and migration 030. For LDK, retain the decimal-string
   `user_channel_id`; use native channel IDs for other backends. Reuse operation
   IDs for retries; inspect uncertain outcomes before new attempts.
6. Keep existing signet reserve/trust policy: inbound/JIT channels require
   anchors plus reserve or the selected-provider waiver for at most 200,000
   sats per channel. Recovery verification needs the same reserve or waiver.
7. Prefer rolling forward on failure. rc18 lacks migration-030 operation
   tracking/reconciliation; do not blindly roll back and replay requests.
   Preserve latest state and follow [rollback constraints](../UPGRADING.md#rollback-constraints).
