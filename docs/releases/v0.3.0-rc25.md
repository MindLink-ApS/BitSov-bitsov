## Behaviour changes and known limits

**New switches, all off by default.** `[calls] call_continuity_v1` (#612,
#622), `[calls] call_reply_free_v1` (#613, #616, #621), `[pairing]
standing_allowance_v1` (#614, #617, #620) and `[pairing]
unattended_device_approvals` (#508). Anything but a literal `true` leaves each
off. With a switch off, behaviour is unchanged. `GET /api/v1/status` lists the
three `_v1` capabilities only while they are on. Known limits from the PRs:

- With `call_reply_free_v1`, the callee still needs a spend-scoped token to
  submit the reply and attach call media; the reply is free, not grant-free.
  A free reply goes only to a caller whose node also advertises the switch.
- With `call_continuity_v1`, breaker rate limits do not count a carried hold
  again against the renewed grant. Only the party that placed a call holds a
  hold, so only that party's app can hang up after its grant expired.
- `standing_allowance_v1` is reachable only through the `pair-ticket` owner
  channel. There is no owner-facing view of the terms and no way to change
  them on an existing pairing. The ledger is conservative and may hold back
  unspent sats for up to the window length plus the longest call.
- `unattended_device_approvals`: whoever gets the disk and the stored unlock
  secret can approve as the owner. It is refused for a plaintext seed, an
  unlock secret on the command line and a machine declared as run for someone
  else.

**Payments.** Keysend message payments go only to a Lightning key the
contact's identity signed (#440). An older contact that advertises an unsigned
key is refused with "contact must update", without an invoice fallback; an
older node can still pay an rc25 node. Every message or call send to a peer
without an open session needs an explicit `max_total_msat` (#578). A settled
payment is counted while chain sync has lapsed (#509).

**Calls.** Invites wait for a paired device before ringing and end with
`call_not_reachable` when none receives them (#586, #593). Block invoices are
minted only at the callee's current, floored minute price; `call_price_changed`
ends the call and releases its unused hold (#496, #604). Media teardown is
journaled and replayed; on restart a callee's previously attached live call
ends with a hangup and its remaining prepaid coverage cannot be used (#574).
**Update both nodes before paid calls.** Do not run paid calls while versions
are mixed, as for rc24.

**Network and setup.** `init` and `restore` take `--network` (default
`signet`). `start` refuses an unapproved mainnet config with
`mainnet_not_approved` until `[node] allow_mainnet = true` is added by hand,
including a start with no config file, and refuses a known public server on
another network (#581). `bootstrap/state` reports `network` (#443); CLN network
values are normalized like LDK ones (#589). Esplora tips are recovered through
configured fallbacks (#601).

**Pairing and security.** Relation intents are v2 and bound to the pairing
epoch; v1 is refused (#478). Long-lived secrets come from operating-system
randomness (#582). Skipped group message keys are capped across all senders
(#473). Inbound calendar payloads are bounded before copy or expansion (#585).
A pending elevation request reads `granted` only when a live owner window
covers its terms (#620). Compound readiness discovery is read-only and grants
no authority (#606).

The [rc24 known limits](v0.3.0-rc24.md#paid-call-behaviour-and-known-limits)
remain, including disconnect recording and peer notification for media-drop
hangups. Retain existing operation IDs when resolving uncertain paid results;
do not create a new paid operation to clear an uncertain result. Advisory
waivers for RUSTSEC-2026-0459 expire on 2026-12-09 and for the `chrono` and
`chrono-tz` maintenance notices on 2026-12-20.

## Wire, storage and compatibility

Forward-only migrations **040** (call media teardown intents), **041** (call
offer binding) and **042** (free call reply receipts) apply on SQLite and
PostgreSQL. Pairing storage remains v8; new pairing fields are optional. The
`LightningInfo` frame gains an optional identity signature (#440); relation
intents use the `bitsov-relation-intent-v2` domain (#478).

An older binary refuses a config that sets any new `[calls]`, `[pairing]` or
`[node]` key. Nodes coming from rc23 or earlier must also follow
[rc23 → rc24](../UPGRADING.md#rc23--rc24) and, from rc22 or earlier,
[rc22 → rc23](../UPGRADING.md#rc22--rc23). Existing
[rollback constraints](../UPGRADING.md#rollback-constraints) remain.

## 4. Retained nodes: rc24 → rc25

These steps are for a future signed release. Rehearse on disposable regtest
data before a retained signet node.

1. Record the running binary/version, service command, configuration and data
   locations on both nodes. End calls and reconcile pending payments using
   their existing IDs. Stop only BitSov; leave separately managed Lightning
   backends alone. Do not run paid calls during the mixed-version interval.
2. Take a consistent backup of the complete BitSov data directory and, for
   PostgreSQL, its database. Retain config, wallet/channel, pairing, session
   and operation state together. A backup is not permission to rewind a live
   node after new state has been written.
3. Verify the future signed artifact for the correct platform, stage it beside
   the retained binary, and confirm `--version` reports `konsensus 0.3.0-rc25`.
   Check `[lightning] network` and the `[chain]` URLs: a mainnet config needs
   `[node] allow_mainnet = true` added by hand, and a known public server on
   another network is refused. Leave the new switches off unless deliberately
   enabled.
4. Switch the BitSov binary and start with the retained config, data and normal
   owner controls. Do not re-run `init`. First start applies migrations 040,
   041 and 042. Earlier nodes must also complete the steps for rc23 → rc24
   and rc22 → rc23.
5. Inspect migration logs. Keep all completion markers and investigate
   unreadable or unwritable data. Check owner `node_version`, health, identity,
   contacts, channels, chain source and `money_ready`; normal initial wallet
   sync does not establish payment readiness. Resolve `chain_unavailable` by
   restoring source availability and freshness before priced work. Repeat the
   upgrade on the other node and confirm both report rc25 before any paid
   message or call.
6. Read session state on both peers, then confirm one paid message in each
   direction on signet; keysend payments need the peer's signed Lightning key.
   Reconcile pending results before retrying. With both nodes on rc25, wait
   until both report payment-ready (`money_ready` is true) and their channels
   are usable, then check a call through the paired device and its closing
   result within the configured cap. Keep the upgraded data intact.

## 5. Rollback and recovery

Prefer rolling forward with the latest complete state. No retained-node
rc25 → rc24 rollback rehearsal is recorded. Before replacing an installed
candidate, end calls, reconcile operations and preserve the current complete
state.

Do not run rc24 or older on data opened by rc25. There is no in-place reverse
migration for 040–042 on SQLite or PostgreSQL. Keep migration rows and
completion markers. Remove any new `[calls]`, `[pairing]` or `[node]` keys
before an older binary reads the config. Never restore an older database
beneath newer wallet/channel, pairing or ratchet state, or remove payment
receipts to make an old binary start. Follow
[rollback constraints](../UPGRADING.md#rollback-constraints), preserve unresolved
operation IDs and repeat upgrade checks after a forward repair.
