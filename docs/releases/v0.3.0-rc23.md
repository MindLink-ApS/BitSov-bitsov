## Known limits

**Mixed rc22/rc23 deferred messages may stall.** #548's recovery handover is not
fully supported by rc22. Mixed rc22/rc23 deferred messages may reach **10 attempts**
and be marked `stalled`; an upgrade does not establish their delivery or refund.
Reconcile the existing operation IDs and payment results on both peers before
retrying. Do not create a new paid operation to clear an uncertain result.

**Migration 038/039 rollback needs a database restore.** These migrations have
no in-place downgrade. On SQLite, crossing back requires restoring the
pre-upgrade `konsensus.db` as part of a consistent-state recovery plan, not
deleting migration rows. A database-only rewind beneath newer wallet, channel,
pairing or session state is not a supported recovery. Prefer rolling forward;
see [rollback](#5-rollback-and-recovery).

**SQLite waiver until 2026-12-09.** #547 records a temporary applicability
waiver, not a patched SQLite dependency. It covers only exclusively trusted
local database and WAL provenance across SQLx, LDK, tower and durable-relay
stores. Custom paths, operator-prepared databases and restored backups need the
same provenance. Untrusted or externally writable database/WAL files are outside
the waiver. Review or remove it before **2026-12-09T00:00:00Z**, the OSV expiry.
A coordinated dependency upgrade remains outstanding.

**Inbound connection saturation.** #545 caps concurrent accepted inbound
connections at **512 across all listening addresses**. There are no reserved
slots for channel peers: when all slots are occupied, a new inbound connection
from a channel peer is also closed. Existing connections and outbound reconnects
are unaffected. A peer with a persisted address can be reached outbound; one
without must retry after a slot frees. The cap bounds admission; it does not
guarantee availability under saturation.

**An explorer tip is a third party's view.** #544 reports an unaccepted default
public explorer but leaves the source in use. A fresh tip on the expected
network is still the explorer's assertion, not independent chain validation.
`konsensus chain-tip --config <config>` only reports the configured source.
Choose a source you operate, or explicitly accept the explorer under `[chain]`
with `accept_third_party_tip = true` where supported; neither the flag nor the
status label establishes correctness. See [existing explorer nodes](../CHAIN-SOURCE.md#existing-nodes-on-a-public-explorer).

**PostgreSQL rollback is not fenced by released binaries.** #504 protects the
candidate against schemas newer than it knows. Released rc22 and older
PostgreSQL binaries skip unknown migration versions and may start on this
candidate's database. Do not run them there. SQLite refuses a database carrying
migration 033 with `VersionMissing`; this is a refusal, not a downgrade path.
See [rollback](#5-rollback-and-recovery).

**Session and chain limits remain.** Read session state on both peers before
retrying a paid send after a reconnect. Use Check pending result for an app's
pending operation; use End call or Hang up for a call still shown by the app.
Do not resend an uncertain paid operation with a new ID. The
[retained-release recovery guide](../operations/e2ee-session-recovery.md) is
specifically for rc21 and rc22. Chain network checks also retain their documented
limits: custom signets share genesis, and a real chain source is not
network-checked with LND, LNbits or mock Lightning, which supply no network to
that check. Direct invoice and keysend payments, including paired spend-grant
payments, remain outside the peer-price tip check; their grant limits still
apply. On-chain sends, channel opens, liquidity and sponsor gifts are also
outside that check, as are the dormant daily hosting keysend and opt-in invite
auto-channel opens. See [network check](../CHAIN-SOURCE.md#network-check) and
[tip readiness](../CHAIN-SOURCE.md#tip-readiness).

## Wire and storage

The peer wire definitions under `konsensus-message/src/wire` are unchanged in
this window. That observation alone does not establish mixed-version operation.
Owner API additions include `node_version`, `max_call_minutes`, calendar
`failed_for` and optional `chain_view.explorer_default`; raised call media limits
also add a handshake response header. Clients must tolerate these additions.
The recovery handover adds `session_handover` refusal/retry handling without
changing those wire definitions. Unchanged definitions do not give rc22 the
candidate's deferral and paid-envelope replacement behavior. Clients must retain
the existing operation ID and distinguish an unpaid send held before dispatch
from an already-paid operation awaiting session recovery.

Retained configurations can now be refused for a tier mismatch or an
unacknowledged non-loopback owner API bind. The optional media-limit keys and
`accept_third_party_tip` are newer than rc22; older binaries reject unknown
configuration keys. Removing keys does not reverse a storage upgrade.

## Migrations

- **033** is new since rc22 on both SQLite and PostgreSQL. It supplies schema
  parity and calendar/onboarding repairs; no down migration is provided.
- **038** adds durable envelope deferrals and **039** adds their expiry and
  expiry index. Both SQLite and PostgreSQL register these migrations. Existing
  deferrals without an expiry expire on upgrade. Neither migration provides an
  in-place downgrade; a SQLite rollback requires restoring pre-upgrade
  `konsensus.db` within the consistent-state constraints below.
- #467 upgrades encrypted records, cached plaintext and persisted sessions to
  the location-bound format. A background pass converts readable fields and
  retains a completion marker; inspect aggregate upgrade logs for unreadable or
  unwritable fields and follow up before treating the upgrade as complete.
  Keep the current markers across restarts and storage-mode changes.
- Pairing storage remains **v8**. This does not make an older binary compatible
  with migrations 033, 038 or 039, or the encrypted record format.
- Follow [location-bound storage records](../UPGRADING.md#location-bound-storage-records-after-rc22)
  and the existing [rollback constraints](../UPGRADING.md#rollback-constraints).
  Prefer rolling forward with the latest consistent state.

## 4. Retained nodes: rc22 → rc23

These are steps for a future signed release, not instructions to install this
draft. Rehearse on disposable regtest data before a retained signet node.

1. Record the running binary/version, service command, configuration and data
   locations. End calls and reconcile pending payments with their existing IDs.
   Stop only BitSov, leaving any separately managed Lightning backend alone.
2. Take a consistent backup of the complete BitSov data directory and, for
   PostgreSQL, its database. Retain config, wallet/channel, pairing, session and
   operation state together. Do not treat the backup as permission to rewind a
   live node after new state has been written.
3. Verify the future signed artifact for the correct platform, stage it beside
   the retained binary, and check `--version`. Resolve tier consistency and API
   bind settings. Review optional media settings and the configured chain source
   using `chain-tip`; do not change or accept a source implicitly.
4. Switch the BitSov binary and start with the retained config, data and normal
   owner-control options. Do not re-run `init`. First start applies migrations
   033, 038 and 039 and starts the encrypted record upgrade: from this point,
   use the forward-only recovery rules below.
5. Inspect migration and aggregate record-upgrade logs. Keep all completion
   markers and investigate unreadable or unwritable data. Check owner
   `node_version`, health, identity, contacts, channels, chain source and
   `money_ready`; normal initial wallet sync does not mean payments are ready.
   If `chain_unavailable` appears, restore source availability and freshness
   before initiating priced work.
6. Read session state on both peers, then confirm one message in each direction
   on signet. Reconcile any pending result before retrying. Check a call and its
   closing result within the configured cap; this is not real-hardware cutoff
   evidence until recorded. Keep the upgraded data intact.

## 5. Rollback and recovery

1. **Before the candidate has opened the retained database**, an abandoned
   installation can switch back to the previously verified rc22 binary and its
   retained config, provided no candidate migration or state write occurred.
   Confirm that condition; uncertainty belongs to the next step.
2. **After first candidate start, do not downgrade to rc22 or older.** Stop
   BitSov if recovery is needed, preserve the latest complete state, and repair
   or replace the candidate by rolling forward with a compatible binary. There
   is no supported in-place reverse migration or record-format downgrade.
3. On SQLite, leave the migration history and format markers intact when an old
   binary refuses startup. On PostgreSQL, prevent the service from launching a
   released older binary even if it would start; absence of refusal does not
   establish compatibility. Never delete migration rows or completion markers.
4. Do not restore an older database beneath current wallet, channel, pairing or
   ratchet state, or remove payment receipts to make an older binary start.
   Any backup recovery needs a separately established consistent-state plan
   under [UPGRADING](../UPGRADING.md#rollback-constraints).
5. After a forward repair, restart with the latest consistent data and repeat
   the upgrade checks. Preserve unresolved operation IDs and reconcile their
   results before further spending. No rc23 → rc22 rollback rehearsal is claimed
   by these notes.
6. A rollback across migrations **038/039** requires restoring a pre-upgrade
   `konsensus.db` on SQLite, not an in-place schema reversal. This is a backup
   recovery under a separately established consistent-state plan, subject to
   step 4 and the encrypted record markers; it is not permission to run rc22
   on the candidate's data. PostgreSQL also has no down migration; recover only
   from a consistent backup under that plan or roll forward.
