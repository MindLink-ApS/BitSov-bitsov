# BitSov v0.3.0-rc22 — operator signing checklist

**Pre-release.** Not for production use. rc22 is a security update: rc21
(`v0.3.0-rc21`, `b3f1ad1`) plus `78ba6b4` (#512), `2eae3fe` (#505), `5179ed9`
(#519), `9083dfa` (#520) and `9c923c9` (#521). Re-pin the bundled app node only after a signed rc22 is published and
verified. This preparation does not sign, tag or publish.

## Scope

| Area | PR | Operator impact |
|---|---|---|
| E2EE send | #519 | An E2EE send now saves its advanced send chain before the ciphertext leaves the session; if the save fails, nothing is sent. Chat, call signals, files and RSVPs are refused with `not_dispatched`, reason `session_save_failed`, before any payment for that send. An admission already settled in the same call stays settled and is reported as paid, with the same reason. In a room or calendar fan-out, that recipient is skipped and nothing is paid to it. Saves and deletes of session state run to completion under the session lock even if the request that started them goes away. |
| Session setup | #520 | Session setup applies stricter consistency checks to the keys it receives. A prekey bundle or session init that fails them is refused before anything changes; the node logs a warning and adds no reply frame. One-time prekey id values change; the field and its type do not. No config change. |
| File sends | #521 | File sends report the routing fee actually paid. `POST /api/v1/files/:id/send` returns optional `fee_paid_msat`, omitted when any component fee is unknown and on backends other than LDK; absence does not mean zero. |
| Docs | #512 | Docs say what encryption covers today: message content and call audio are encrypted between nodes, and either node can read them. Encryption that reaches the app is planned. No behaviour change. |
| Dependency audit config | #505 | RUSTSEC-2026-0429 is waived in the audit, deny and OSV configs for the test-only `zip` 0.6.6, which is absent from the shipped binary. No change to any dependency. |

Release metadata: all 14 workspace packages and `Cargo.lock` report
`0.3.0-rc22`; dependency versions are unchanged.

## Not included

- Call cutoff is not yet verified on real hardware.
- This release does not fix the other open reports.
- The send change does not extend to a database restored from an older copy.
  Keep following the [rollback constraints](../UPGRADING.md#rollback-constraints).
- The session setup checks are consistency checks only; they make no wider
  statement about a peer's keys.

## Known limit

Also present in rc21. If a link drops during a call and both nodes reconnect at nearly the same moment,
the two nodes can end up on different sessions. Messages and call minutes sent
then can be paid for and not read. It can clear within about a minute; otherwise
follow the steps below. This release does not change it, and a fix is planned.

If messages stop being read after a dropped link:

1. Stop sending; a send can be paid for and not read.
2. Restart one node with its existing config and data, and allow up to about 90
   seconds; early sends may fail with nothing paid.
3. In any app that reports a pending result, use Check pending result.
4. In any app that still shows the call, use End.
5. Check that messages are read in both directions, then call again.

Amounts already paid for messages or minutes that were not read are not refunded.
Tested on regtest on this release and on rc21, by calling the app's host
functions, not on real hardware.

## Wire and storage

The diff from `v0.3.0-rc21` to `9c923c9` changes no frame, envelope, ratchet
message, prekey bundle or session init format, and no stored session state
format:

- `konsensus-message/src/wire` is unchanged. The `konsensus-message` change is an
  in-process event field that carries what a connection established.
- In `konsensus-crypto`, the message, bundle, init and state types and their
  serialization, the encryption inputs and the receive path are unchanged. A send
  builds the same message format. One-time prekeys stay in memory.
- `konsensus-core`, `konsensus-storage`, the other crates outside `konsensus-api`,
  `konsensus-crypto`, `konsensus-message` and `konsensus-node`, `vendor`,
  `Cargo.lock`, `scripts` and `.github` are unchanged.

What changes in behaviour:

- **Seen by a peer:** an rc22 node refuses a prekey bundle or session init that
  fails the stricter checks and adds no reply frame, so that peer gets no new
  session from it. When a local save fails, no ratchet init is sent and the session
  stays. One-time prekey id values change within the same `u32` field.
- **Owner API only:** the `session_save_failed` reason and the optional
  `fee_paid_msat` on file sends.

From the source, the bundles and inits an rc21 node builds pass the stricter
checks, so rc21 and rc22 should interoperate. The source supports this
reading, and it was also run on regtest (below); not on real hardware.

Mixed rc21 and rc22 operation: tested on regtest at `9c923c98`. Upgrade in place
in both id orders, fresh sessions and file sends to and from rc21 passed. Not run
on real hardware.

Rollback from rc22 to rc21: tested on regtest in both id orders. rc21 started on
the candidate's data, and chat, calls and files passed. The earlier guidance that
prefers rolling forward stands.

## 2. Dry-run gate, then sign (operator only)

- [ ] Run `scripts/release-sign.sh --dry-run v0.3.0-rc22` on the operator's Mac and investigate any darwin-aarch64 rebuild mismatch; never break-glass under time pressure.

**This gate precedes any real artifact signing.** The line above names the
required dry-run; the current script also requires `<merged sha>` and an
explicit waiver for each non-host target. It requires an **existing signed tag**
and CI draft assets: it will not create a tag in dry-run mode. Thus an untagged
prep cannot yet complete this gate. Initial tag signing, which triggers CI,
is a separate operator prerequisite; it does not approve the CI binaries.
Do not use a normal signer invocation merely to get past this prerequisite:
it would continue toward artifact signing without the completed dry-run.
No tag or key operation is authorized or performed by this preparation.

For an Apple Silicon Mac (`aarch64-apple-darwin`), after the operator has
separately established the reviewed signed tag and draft, the full dry-run is:

```sh
scripts/release-sign.sh --dry-run \
  --accept-unverified-target x86_64-apple-darwin \
  --accept-unverified-target aarch64-unknown-linux-gnu \
  --accept-unverified-target x86_64-unknown-linux-gnu \
  --accept-unverified-target x86_64-pc-windows-msvc \
  v0.3.0-rc22 <merged sha>
```

Each target waiver requires a separate operator decision and recorded rationale;
these flags are not evidence of an independent rebuild. If using a different
host, adjust the waivers to exclude that host. Follow the
[RC template](RC_CHECKLIST_TEMPLATE.md) and
[release policy](../ops/RELEASE_POLICY.md).

- [ ] Confirm the tag resolves to `<merged sha>` on `origin/main`, the CI build

- [ ] Confirm signature validation uses an anchored `[GNUPG:] VALIDSIG` record

## 4. Retained nodes: rc21 → rc22

1. Record the current BitSov binary/version, config, data directory, service
   command and signet network. Let calls end and reconcile pending payments.
2. Take a consistent database backup. No migrations run for rc21 → rc22; retain
   the latest data and seed, and preserve the existing rollback fences.
3. Verify the signed artifact for the node's OS/architecture; stage rc22 next
   to rc21 and confirm `konsensus 0.3.0-rc22`. Do not re-run `init` or restore
   a historical snapshot.
4. Stop only BitSov, switch its binary path, and restart with the retained
   config/data and intended owner-control/startup options. Never stop,
   reconfigure or modify a Lightning backend or wallet that BitSov does not own.
   No config change or grant re-issue is needed.
5. Check version, `/api/v1/health`, node identity, contacts/channels and signet
   status. Exchange a message with a contact in each direction. If a send is
   refused with reason `session_save_failed`, check disk and database health. If
   a session with a contact does not form, read the node log.
6. Prefer rolling forward with the retained data. Continue to follow the
   existing [rollback constraints](../UPGRADING.md#rollback-constraints) and
   [rc21 → rc22](../UPGRADING.md#rc21--rc22).
